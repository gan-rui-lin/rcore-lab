# 多架构移植：启动流程如何屏蔽架构差异

**日期**: 2026/3/6
**父文档**: [多架构移植分析_OSKernel2025-rustoswhu.md](多架构移植分析_OSKernel2025-rustoswhu.md)

---

## 一、问题域：启动流程为什么无法完全统一

启动流程是架构差异最大、最难抽象的部分。原因在于：

1. **启动协议不同**：RISC-V 用 SBI，x86 用 Multiboot/UEFI，AArch64 用设备树，LoongArch 用直接映射窗口
2. **初始分页方式不同**：需要在没有 MMU 的情况下建立初始页表
3. **特权级跳转不同**：ARM 需要从 EL3 降到 EL1，RISC-V 从 M-mode 跳到 S-mode
4. **内存布局不同**：内核加载地址、虚拟地址起始完全不同

**rustoswhu 的策略**：启动流程不做统一抽象，每个架构完全独立实现，只要最终调用 `ArchInterface::main(hartid)` 进入通用内核即可。

---

## 二、统一的目标

无论哪个架构，启动完成后必须达到以下状态：

```
┌─────────────────────────────────────┐
│  ArchInterface::main(hartid)        │  ← 所有架构最终到这里
├─────────────────────────────────────┤
│  已启用的状态：                       │
│  ✓ 分页（MMU 启用）                  │
│  ✓ 内核态栈（SP 有效）               │
│  ✓ BSS 段清零                       │
│  ✓ 日志系统初始化                    │
│  ✓ 中断向量注册                      │
│  ✓ 物理内存区域已通告                 │
└─────────────────────────────────────┘
```

## 三、各架构启动流程对比

### 3.1 RISC-V 64 (`arch/src/riscv64/entry.rs`)

```
OpenSBI (M-mode)
    │
    ▼
_start (S-mode, 物理地址)
    │ 1. 设置栈指针 (bootstack + VIRT_ADDR_START)
    │ 2. 建立初始页表 PAGE_TABLE[]
    │    ├─ 恒等映射: 0x8000_0000 → 0x8000_0000 (1GB 大页)
    │    └─ 高半映射: 0xffff_ffc0_8000_0000 → 0x8000_0000
    │ 3. 写 satp CSR 启用 Sv39 分页
    │ 4. sfence.vma 刷新 TLB
    │ 5. 跳转到虚拟地址的 rust_main
    ▼
rust_main (S-mode, 虚拟地址)
    │ 1. clear_bss()
    │ 2. init_logging()
    │ 3. 解析设备树 → add_memory_region()
    │ 4. init_interrupt()
    │ 5. prepare_drivers()
    ▼
ArchInterface::main(hartid)
```

**关键代码**：
```rust
#[naked]
unsafe extern "C" fn _start() -> ! {
    asm!(
        "la     sp, {boot_stack}",       // 加载栈地址
        "li     t0, {vaddr_start}",
        "or     sp, sp, t0",            // SP 转为虚拟地址
        "la     t1, {page_table}",
        "srli   t1, t1, 12",
        "li     t0, 8 << 60",
        "or     t1, t1, t0",
        "csrw   satp, t1",              // 启用 Sv39
        "sfence.vma",
        "la     a2, rust_main",
        "or     a2, a2, t0",
        "jalr   a2",                    // 跳转到虚拟地址
        ...
    )
}
```

### 3.2 AArch64 (`arch/src/aarch64/boot.rs`)

```
Firmware (EL3)
    │
    ▼
_start (EL2/EL3)
    │ 1. 保存 CPU ID (MPIDR_EL1 → x19)
    │ 2. 保存设备树指针 (x0 → x20)
    │ 3. 设置栈指针
    ▼
switch_to_el1()
    │ 1. 配置 HCR_EL2 (RW=1, 让 EL1 运行在 AArch64)
    │ 2. 配置 CNTHCTL_EL2 (允许 EL1 访问定时器)
    │ 3. 设置 SPSR_EL2 (目标 EL1h, 中断屏蔽)
    │ 4. eret 降级到 EL1
    ▼
init_boot_page_table()
    │ 建立初始页表 BOOT_PT_L1
    │ ├─ 恒等映射 (VA = PA)
    │ └─ 高半映射 (VA = PA | VIRT_ADDR_START)
    ▼
init_mmu()
    │ 1. 设置 MAIR_EL1 (内存属性)
    │ 2. 设置 TCR_EL1 (4KB 页, 39-bit VA, 40-bit PA)
    │ 3. 写 TTBR0_EL1 和 TTBR1_EL1
    │ 4. 设置 SCTLR_EL1 (启用 MMU + Cache)
    │ 5. isb 指令屏障
    ▼
rust_main (EL1, 虚拟地址)
    ▼
ArchInterface::main(hartid)
```

AArch64 特有的复杂性在于**需要从高特权级（EL3/EL2）降到 EL1**，以及配置 MAIR（内存属性间接寄存器）来定义缓存策略。

### 3.3 x86-64 (`arch/src/x86_64/multiboot.rs`)

```
BIOS/UEFI → GRUB (Multiboot)
    │
    ▼
multiboot.S (16-bit → 32-bit → 64-bit)
    │ 1. Multiboot header magic (0x1BADB002)
    │ 2. 从实模式切换到保护模式
    │ 3. 配置 CR0 (PE, PG, WP, NE)
    │ 4. 配置 CR4 (PAE, PGE, FXSR)
    │ 5. 配置 EFER MSR (LME, NXE) 启用长模式
    │ 6. 建立初始四级页表
    │ 7. 远跳转到 64 位代码段
    ▼
rust_tmp_main (Ring 0, 虚拟地址)
    │ 1. 清零 BSS
    │ 2. 初始化 IDT (中断描述符表)
    │ 3. 初始化 APIC (高级可编程中断控制器)
    │ 4. 初始化信号跳板
    │ 5. 解析 Multiboot 信息 → 内存区域
    ▼
ArchInterface::main(hartid)
```

x86-64 是最复杂的启动流程，因为需要经历 **实模式 → 保护模式 → 长模式** 三次模式切换。

### 3.4 LoongArch64 (`arch/src/loongarch64/boot.rs`)

```
Firmware
    │
    ▼
_start (PLV0)
    │ 1. 设置直接映射窗口 (DMW0: UC, DMW1: CA)
    │    DMW0: 0x8000_xxxx → 物理地址 (非缓存)
    │    DMW1: 0x9000_xxxx → 物理地址 (缓存)
    │ 2. 启用分页 (CRMD.PG = 1)
    │ 3. 设置 PLV=0, IE=0
    │ 4. 设置栈指针
    │ 5. 读取 CPU ID (CSR 0x20)
    │ 6. jirl 跳转到 rust_main
    ▼
rust_main (PLV0, 虚拟地址)
    │ 1. 初始化控制台
    │ 2. clear_bss()
    │ 3. 初始化中断
    ▼
ArchInterface::main(hartid)
```

LoongArch64 的特点是使用**直接映射窗口**（DMW）而非传统页表来建立初始映射。DMW 是 LoongArch 特有的硬件机制，可以在不建立页表的情况下直接将虚拟地址映射到物理地址。

## 四、初始页表的差异

| 架构 | 初始页表格式 | 映射粒度 | 特殊之处 |
|------|-----------|---------|---------|
| RISC-V | Sv39 二级（1GB 大页） | 1 GB | 同时恒等映射和高半映射，启用后跳转 |
| AArch64 | 一级页表（1GB block） | 1 GB | 需配置 MAIR + TCR，TTBR0/TTBR1 双页表 |
| x86-64 | PML4 四级 | 2MB/1GB | Multiboot 汇编中建立，最复杂 |
| LoongArch | 不需要传统页表 | N/A | DMW 硬件直接映射，无需页表 |

## 五、链接脚本差异

每个架构需要独立的链接脚本来指定加载地址和段布局：

**RISC-V** (`linker-riscv64.ld`):
```ld
BASE_ADDRESS = 0xffffffc080200000;  /* 高半 + 物理 0x80200000 */
```

**x86-64** (`linker-x86_64.ld`):
```ld
BASE_ADDRESS = 0xffffff8000200000;  /* 高半 + 物理 0x200000 */
```

**AArch64** (`linker-aarch64.ld`):
```ld
BASE_ADDRESS = 0xffffff8040080000;  /* 高半 + 物理 0x40080000 */
```

**LoongArch64** (`linker-loongarch64.ld`):
```ld
BASE_ADDRESS = 0x9000000090000000;  /* DMW1 偏移 */
```

所有链接脚本的段结构是一致的（`.text` → `.rodata` → `.data` → `.bss` → `.sigtrx`），只是基址不同。

---

## 六、内存发现机制

各架构发现可用物理内存的方式也不同：

| 架构 | 内存发现方式 | 数据结构 |
|------|-----------|---------|
| RISC-V | 设备树 (FDT) | `/memory` 节点 |
| AArch64 | 设备树 (FDT) | `/memory` 节点 |
| x86-64 | Multiboot info | `mboot_ptr` 传递的内存映射 |
| LoongArch | 设备树或固件表 | BIOS 提供 |

**统一回调**：不管用什么方式发现的内存，最终都调用 `ArchInterface::add_memory_region(start, end)` 通告给内核。

## 七、rcore-lab 的启动流程

rcore-lab 当前的启动流程（`os/src/entry.asm` + `os/src/main.rs`）完全是 RISC-V 的：

```asm
# os/src/entry.asm
    .section .text.entry
    .globl _start
_start:
    la sp, boot_stack_top
    call rust_main
```

**改造要点**：
1. 将 `entry.asm` 移到 `arch/src/riscv64/`
2. 每个架构单独实现启动汇编
3. `os/src/main.rs` 的 `rust_main` 改为实现 `ArchInterface::main(hartid)`
4. `sbi.rs` 移到 `arch/src/riscv64/` 下（其他架构用自己的底层接口）
5. 链接脚本改为 `linker-{arch}.ld` 并通过 `.cargo/config.toml` 选择
