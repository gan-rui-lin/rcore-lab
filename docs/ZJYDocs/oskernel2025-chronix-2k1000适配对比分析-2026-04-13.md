# oskernel2025-chronix 与 rustoswhu 龙芯 2K1000 适配对比分析

日期：2026/04/13

---

## 一、项目背景与整体架构对比

本文分析 **oskernel2025-chronix-retest**（下称 Chronix）在龙芯 2K1000 Vision5 开发板上的适配方案，并与 [rustoswhu 的适配分析文档](OSKernel2025-rustoswhu-2k1000适配分析-2026-04-13.md) 进行横向比较。两个项目均为 OSKernel2025 参赛作品，均宣称支持 LoongArch QEMU 和真实 2K1000 硬件，但在适配思路和技术选型上有根本性差异。

### 1.1 Chronix 项目概述

Chronix 是一个 **设备树（DTB）驱动、硬件抽象层（HAL）分层** 的 Rust 内核，支持：
- RISC-V（QEMU + VisionFive2 星光板）
- LoongArch（QEMU + 2K1000）
- 多核调度（`MAX_PROCESSORS = 4`）

README 明确写道："目前已经适配 RISC-V (QEMU 以及 VisionFive2星光板) 和 LoongArch（QEMU 以及 2K1000）"。

### 1.2 整体架构对比

| 维度 | Chronix | rustoswhu |
|------|---------|-----------|
| 板级配置方式 | 设备树（DTB，运行时解析）| 编译时 `cfg_if!` 宏 + `--cfg board="2k1000"` |
| HAL 分层 | 独立 `hal/` crate，接口严格分离 | `arch/` crate，含 loongarch64/riscv64 各子模块 |
| 页表级数 | 4 级（Sv48 风格，47 位有效地址） | 3 级（39 位有效地址） |
| 多核支持 | 是（SMP，feature 可选） | 否（单核） |
| 内存探测 | DTB + 固定常量 `MEMORY_END = 0x9000_0000_B000_0000` | 固定区间 `0x9000_0000..0x9000_0000+0x2000_0000` |
| Rust toolchain | nightly-2025-01-18 | 未固定（较新 nightly） |

## 二、启动流程与 DMW 窗口配置

### 2.1 DMW 初始化（两者基本一致）

Chronix 与 rustoswhu 的 DMW 初始化方式**几乎完全相同**，均在 `_start` 汇编入口中完成：

```asm
# Chronix: hal/src/component/entry/loongarch64.rs
ori   $t0, $zero, 0x1
lu52i.d $t0, $t0, -2048    # DMWIN0 = 0x8000_xxxx (UC, PLV0)
csrwr $t0, 0x180

ori   $t0, $zero, 0x11
lu52i.d $t0, $t0, -1792    # DMWIN1 = 0x9000_xxxx (CA, PLV0)
csrwr $t0, 0x181
```

两者均遵循标准 LoongArch 规范：
- **DMW0（0x8000 前缀）**：Uncached（UC），用于 MMIO 设备访问
- **DMW1（0x9000 前缀）**：Coherent Cached（CA），用于内核代码和数据

这里的"共识"来自 LoongArch 规范对 MMIO 必须走 UC 窗口的硬性要求，QEMU 对此不作强制，但 2K1000 硬件会严格执行。

### 2.2 虚拟地址跳转（细节差异）

rustoswhu 在 PG 使能后直接以 `la.global` + `jirl` 跳到内核主函数（虚拟地址）。Chronix 则更规范：在 PG 使能后，先对 SP 显式做 `or $sp, $sp, VIRT_RAM_OFFSET` 加上 `0x9000_0000_0000_0000` 偏移，再跳转。这确保了即使 `la.global` 生成的是物理地址，SP 也是正确的内核虚拟地址。

### 2.3 链接基地址

| 项目 | LoongArch 链接基地址 | 对应物理地址 |
|------|---------------------|-------------|
| Chronix | `0x9000_0000_8000_0000` | `0x8000_0000`（2GB）|
| rustoswhu | `0x9000_0000_9000_0000` | `0x9000_0000`（2.25GB）|

两者均通过 DMWIN1（CA）映射内核。Chronix 将内核放在物理 2GB 处（标准龙芯 QEMU 内存起始），rustoswhu 放在 2.25GB 偏移，这在 2K1000 上均有效（板载 1GB DDR3 完整可用）。

## 三、串口驱动适配：最关键差异之一

这是两个项目适配思路分歧最大的地方之一。

### 3.1 Chronix 的早期串口

Chronix 在 HAL 层（`hal/src/component/console/uart.rs`）硬编码早期 UART 地址：

```rust
const UART_ADDR: usize = 0x8000_0000_1fe0_01e0;  // DMW0 窗口，物理地址 0x1fe0_01e0
```

这里存在一个重要问题：**物理地址 `0x1fe001e0` 是 QEMU 模拟 LoongArch virt 机器的 UART 地址，而不是 2K1000 实际硬件上连接到 USB-TTL 串口的 UART**。

根据 rustoswhu 的调研（和我们自己的上板经验），2K1000 Vision5 开发板上连接到 USB-TTL 的 UART2 物理地址是 `0x1fe20000`，而非 `0x1fe001e0`（后者是 UART0，但在 Vision5 开发板上可能未引出或未连接到串口接头）。

这意味着 **Chronix 在 2K1000 上启动时，早期 boot 阶段可能同样没有串口输出**——其早期 UART 使用的是 QEMU 地址。

### 3.2 Chronix 的 OS 级串口驱动（弥补方案）

Chronix OS 层（`os/src/drivers/serial/uart.rs`）在早期 UART 之外实现了一个**更完整的设备树驱动串口**：

- 支持两种兼容字符串：`ns16550a`（标准）和 `snps,dw-apb-uart`（Synopsys DesignWare APB UART）
- 从 DT 解析 `clock-frequency`、`reg-io-width`（寄存器宽度，1字节或4字节）、`reg-shift`（寄存器偏移量）
- **Synopsys 特有的 Busy 中断处理**：当 `is_snps = true` 时，读 offset 31 处的 `USR`（UART Status Register）以清除"busy detect interrupt"——龙芯 2K1000 的 UART 是 Synopsys IP，不清除这个位会导致中断风暴或 UART 卡死
- 寄存器访问支持 `u8`/`u32` 两种模式（某些 LoongArch UART 寄存器间距为 4 字节）

```rust
// os/src/drivers/serial/uart.rs (简化)
if self.is_snps {
    let _usr = self.get_reg::<u8>(31);  // 清除 USR busy interrupt
}
```

龙芯 2K1000 的 UART 是 Synopsys `dw-apb-uart` IP，这个 `is_snps` 路径是**专门为 2K1000 硬件**准备的。相比之下，rustoswhu 使用的是简单的 16550 polling 驱动，没有处理 Snps busy 中断，在某些情况下可能导致 UART 异常。

### 3.3 对比小结

| 方面 | Chronix | rustoswhu |
|------|---------|-----------|
| 早期串口地址 | `0x1fe001e0`（QEMU 地址，2K1000 可能无输出）| `0x1fe20000`（2K1000 实际 UART 地址）|
| 访问窗口 | DMW0（UC，`0x8000` 前缀）✓ | DMW0（UC，`0x8000` 前缀）✓ |
| OS 级驱动 | DT 检测 + Snps busy 处理（更完整）| 简单 16550 polling |
| 换行处理 | 无特殊处理 | 自动补 `\r`（2K1000 需要 `\r\n`）|

## 四、页表 PTE 标志位：不同的"有效页"定义

### 4.1 Chronix 的 PTE 设计

```rust
// hal/src/component/pagetable/loongarch64.rs
// 在每次 map() 时设置
pte.bits |= PTEFlags::MAT_L.bits;  // MAT = 01 (Coherent Cached)
// 用户页：PLV_L | PLV_H (PLV3 = Ring3)
// NX/NR 位用于权限控制（负语义，默认可读可执行）
```

Chronix 的 PTE 默认标志：**`V`（bit 0，Valid）+ `MAT_L`（bit 4，MAT=Coherent Cached）**，对内核页不设置 PLV 位（默认 PLV0）。

### 4.2 rustoswhu 的 PTE 设计

```rust
// arch/src/loongarch64/page_table.rs  
// 注释明确写了 "2k1000"
let mut flags = PTEFlags::V | PTEFlags::P | PTEFlags::MAT_NOCACHE;
```

rustoswhu 的默认标志：**`V`（bit 0）+ `P`（bit 7，物理页存在）+ `MAT_NOCACHE`（bits [5:4]=01，即 Coherent Cached）**。

注意：`MAT_NOCACHE` 这个名字在 bitflags 中有些误导性，其实对应的是 MAT=`01`（Coherent Cached），并非真正的 Uncached。两项目的 MAT 值相同（均为 01b），只是命名不同。

### 4.3 关键差异：`P` 位

**最重要的差异**在于 rustoswhu 强制要求设置 `P` 位（bit 7，Physical/Present），而 Chronix 没有。

LoongArch 页表中，`P` 位表示"物理页确实存在"。在 2K1000 硬件 MMU 中，如果 `P = 0`，即使 `V = 1`，MMU 也可能拒绝翻译（这是比 QEMU 更严格的地方）。rustoswhu 在上板过程中踩坑（用户程序启动即 `InstructionNotExist`）之后才加上这个标志，并留有注释 `//2k1000`。

Chronix 是否会遇到同样的问题？有可能，但 Chronix 主要在 QEMU 上测试，且比赛中主要提交的也是 QEMU 分数，因此可能没有充分暴露这一问题。

### 4.4 PageModifyFault（D 位脏页）处理

Chronix 有一个 rustoswhu 没有的机制：**硬件 D 位脏页处理**（`handle_page_modify_fault`）。

```rust
// hal/src/component/trap/loongarch64/mod.rs
fn handle_page_modify_fault(tf: &TrapContext) -> TrapType {
    // 1. 查 TLB (tlbsrch)
    // 2. 读出 TLB 条目 (tlbrd)
    // 3. 设 tlbelo0/1 的 D bit
    // 4. 写回 TLB (tlbwr)
    // 5. 返回 TrapType::Processed（内核不需要进一步处理）
}
```

LoongArch 硬件页表的 D（Dirty）位机制：初始映射时 D=0，写操作触发 `PageModifyFault`，内核在这里把 D 位置 1 后写回 TLB，再次写操作就不会触发异常。这是一种写时置脏（write-on-demand）优化，节省了初始建立映射时的开销。rustoswhu 则没有实现这个机制，而是在 `map()` 时直接设置 D 位（如果可写则 `flags |= PTEFlags::W | PTEFlags::D`）。

### 4.5 NX/NR 权限位

Chronix 实现了完整的 NX（No Execute）和 NR（No Read）位：

```rust
// 用户可执行页：不设 NX
// 用户只读页：不设 NR，设 NX（不可执行）
// rustoswhu 注释掉了 NX/NR 逻辑
```

rustoswhu 的页表代码中有 NX 相关注释但已注释掉（`// flags |= PTEFlags::NX;`），意味着所有页都是可执行的，存在一定安全风险，但对比赛测试影响不大。

## 五、非对齐内存访问：最大技术差距

这是两个项目在 2K1000 适配上**差距最显著**的地方。

### 5.1 Chronix：完全未处理

搜索 Chronix 整个代码库，没有任何关于 `ALE`（Address Load Error）/ `ALDE`（Address Data Error）异常的处理：

- `TrapType` 枚举中无 `UnalignedAccess` 变体
- `get_trap_type()` 中不处理非对齐异常，会走到 `TrapType::Other`，最终触发 `panic!`
- Cargo config 中无 `-Ctarget-feature=-ual` 或任何相关 flag

这意味着在 2K1000 真实硬件上，**任何产生非对齐内存访问的程序（包括 musl libc、busybox 等）都会导致内核 panic**。

### 5.2 rustoswhu：完整软件模拟

rustoswhu 采用双层防护（详见对应文档）：

1. **编译器层**：`-Ctarget-feature=-ual` 阻止 LLVM 生成非对齐访问指令
2. **陷入层**：`emulate_load_store_insn()` 软件模拟，支持 30+ 种 LoongArch load/store 指令格式（含浮点）

这是有实际上板验证的方案，对应 git commit `e57cf14: feat:add 2k1000 AddressNotAligned handle`。

### 5.3 为何 Chronix 能"过测试"？

QEMU 的 LoongArch 模拟器默认**静默处理**非对齐访问（直接拆分为多次对齐访问），因此在 QEMU 上运行时根本不会触发 `AddressNotAligned` 异常。所有比赛的在线评测都在 QEMU 环境下进行，所以这一缺失不影响比赛得分。

只有在真实 2K1000 硬件上运行才会暴露这个问题。

## 六、块设备驱动：存储介质差异带来的不同选型

### 6.1 Chronix 的 QEMU vs 2K1000 存储

**LoongArch QEMU**：使用 VirtIO PCI Block（`pci_blk.rs`），通过设备树中的 `pci-host-ecam-generic` 节点扫描到 `virtio-blk-pci` 设备，块设备命名为 `sda0`/`sda1`（LoongArch 用 `sda1`）。

**2K1000 硬件**：代码库中有 MMC/SDIO 驱动（`drivers/block/mmc/`），兼容 `snps,dw_mshc`（Synopsys DesignWare Mobile Storage Host Controller），通过 DT 节点 `/soc/sdio` 探测。

但关键问题：**`probe_sdio_blk()` 函数虽然存在，却从未在 `DeviceManager::map_devices()` 中调用**。这意味着 MMC 驱动代码存在但实际上没有接入，2K1000 上的存储驱动在 main 分支是不完整的。

MMC 驱动本身也存在一些可疑实现，如 FIFO 偏移量的硬编码（`0x660` 和 `0x600` 两个值），以及 DMA 结构已定义但调用了 `set_dma(false)`（使用 polling 模式）。

### 6.2 rustoswhu 的 SATA/AHCI 方案

rustoswhu 完整实现了 AHCI 驱动（`isomorphic_drivers::block::ahci::AHCI`），通过 PCI 总线扫描定位 AHCI 控制器（class=0x01, subclass=0x06, prog_if=0x01），并实际完成了上板验证。

2K1000 Vision5 开发板使用 SATA 硬盘接口，rustoswhu 选择了 AHCI，这是正确的技术选型。

### 6.3 对比

| 方面 | Chronix | rustoswhu |
|------|---------|-----------|
| 2K1000 目标驱动 | MMC/SDIO（snps,dw_mshc） | SATA/AHCI（PCI 扫描）|
| 驱动接入状态 | **未接入**（代码存在但未调用）| 已接入且验证 |
| QEMU 驱动 | VirtIO PCI（DT 驱动）| VirtIO PCI（PCI 扫描）|
| 文件系统烧录 | 未记录（MMC 驱动未完成）| TFTP 分块传输 + uboot scsi write |

这里值得注意：2K1000 Vision5 实际上有 **SATA 接口**（标准 SATA 硬盘或 SSD），而 **不是 SD 卡**。Chronix 的 MMC/SDIO 驱动针对的是 VisionFive2 或具有 microSD 卡的开发板，用在 2K1000 上从根本上就目标错了。这可能是 Chronix 在 2K1000 上无法完整运行的核心原因之一。

## 七、中断控制器适配

### 7.1 Chronix 的两套方案

Chronix 为 LoongArch 实现了完整的中断控制器栈，这是 rustoswhu 完全没有的部分：

**EXTIOI（扩展 IO 中断控制器）**：通过 IOCSR 寄存器访问：
- `0x1600`：中断使能
- `0x1680`：自动轮转使能
- `0x1800`：每核中断状态
- `0x14C0`/`0x1C00`：中断路由配置

**Platic / LS7A PCH-PIC**：通过 MMIO 访问，物理地址 `0x1000_0000`（DT 节点 `"loongson,pch-pic-1.0"`）。

**main 分支**：使用设备树解析，动态确定中断控制器地址。

**onsite 分支**（commit `669aea9`）：为 2K1000 上板改用硬编码地址：
```rust
pub const LS7A_PCH_REG_BASE: usize = 0x1000_0000 + 0x8000_0000_0000_0000;
// = 0x8000_0000_1000_0000，走 DMW0 UC 窗口
```
该 commit 的注释："From https://github.com/Godones/rCoreloongArch"，即参考了另一个龙芯 rCore 实现。

### 7.2 rustoswhu 不需要中断

rustoswhu 使用**轮询（polling）模式**处理 IO，定时器中断通过 LoongArch 内部定时器（TI 中断，irq_num=11）处理，无需 LS7A 外部中断控制器。这极大简化了上板难度，但也意味着无法支持复杂外设（网络等）。

### 7.3 中断控制器的重要性

对于完整的 2K1000 支持，正确的中断配置**至关重要**：
- 键盘/鼠标输入
- 块设备（SATA/MMC）完成中断（否则只能 polling）
- 网络设备
- USB 等

Chronix 在这方面的工作量远大于 rustoswhu，但 onsite 分支才有真正可用的硬件中断实现。

## 八、编译配置对比

### 8.1 目标架构 feature 控制

| 编译选项 | Chronix | rustoswhu |
|---------|---------|-----------|
| `-Ctarget-feature=-ual` | **无**（不禁用非对齐访问）| **有**（禁止 LLVM 生成非对齐指令）|
| `-Ctarget-feature=-lsx,-lasx` | **有**（禁用 LSX/LASX 向量扩展）| **无** |
| `--cfg board="2k1000"` | **无**（使用 DT 运行时检测）| **有**（编译时选择路径）|
| `frame-pointers` | `yes` | `yes` |

**`-lsx,-lasx` 的意义**：LoongArch 有 128 位 LSX 和 256 位 LASX 向量扩展指令集。2K1000 芯片支持 LSX 但部分版本不支持 LASX；禁用这两个 feature 可以避免 LLVM 自动生成向量指令，防止在不支持 LASX 的 2K1000 上触发"非法指令"异常。这是 Chronix 独有的处理，rustoswhu 没有考虑到这一点。

### 8.2 板级配置方式的根本差异

| 方面 | Chronix（DT 驱动）| rustoswhu（cfg 驱动）|
|------|-----------------|-------------------|
| UART 地址 | 运行时从 DTB 解析（OS 层）| 编译时 `cfg_if!` 选择 |
| 内存范围 | DTB `memory` 节点 + 固定常量 | 固定硬编码常量 |
| PCI 设备 | DTB `pci-host-ecam-generic` | 硬编码 `PCI_CONFIG_ADDRESS` |
| 中断控制器 | DTB `loongson,pch-pic-1.0` | 无（不需要）|
| 可移植性 | 更高（理论上换板只需换 DTB）| 低（换板需重新编译）|

Chronix 的 DT 驱动架构更接近生产级内核的设计，但需要 U-Boot 在启动时正确传递 DTB，且 DTB 内容必须准确描述 2K1000 的硬件。

## 九、陷入向量与用户态切换

### 9.1 Chronix 的 trap.S

Chronix 的 `hal/src/component/trap/loongarch64/trap.S` 实现了三套向量：
- `__trap_from_user`：用户态陷入（通过 KSAVE_CTX 切换到内核上下文）
- `__restore`：返回用户态（从 TrapContext 恢复所有寄存器）
- `__trap_from_kernel`：内核态陷入（仅保存 caller-saved 寄存器）

用户地址探测（`__user_rw_trap_vector` + `__user_rw_exception_entry`）：实现了 Linux 内核 `copy_from_user` 类似的安全机制——若陷入处理中访问用户地址时发生 pagefault，异常入口直接将 ERA 推进 4 字节并返回错误码，而非 panic。**这是 2K1000 上需要 4KB 对齐的关键入口**，Chronix 在 trap.S 中对此有 `.align 12`（即 4096 字节对齐）保证，与 rustoswhu 的 `.balign 4096` 注释 `//2k1000需要4096对齐` 保持一致。

### 9.2 主要对比

| 方面 | Chronix | rustoswhu |
|------|---------|-----------|
| 陷入向量对齐 | `.align 12`（4KB）| `.balign 4096`，注释说明 2K1000 需要 |
| 内核态陷入 | 独立 `__trap_from_kernel` | 检查 PLV 位后原地处理 |
| 浮点懒加载 | `FloatingPointUnavailable` → 置 FP 脏标记 | 直接 enable FP（`euen::set_fpe(true)`）|
| 信号 trampoline | 完整 UContext + sigtrx 汇编 | 简单 sigtrx 汇编 |

## 十、综合对比总结

### 10.1 技术成熟度横向比较

| 核心适配点 | Chronix | rustoswhu | 谁更适合 2K1000 |
|-----------|---------|-----------|---------------|
| DMW 初始化 | ✅ 正确 | ✅ 正确 | 平手 |
| 早期串口 | ⚠️ 地址可能不匹配 2K1000 | ✅ 正确地址 | rustoswhu |
| OS 串口驱动 | ✅ 支持 Snps 特性 | ⚠️ 简单 16550 polling | Chronix |
| 非对齐访问 | ❌ 未处理 | ✅ 完整软件模拟 | rustoswhu |

| 4KB 陷入对齐 | ✅ | ✅ | 平手 |

### 10.2 根本性差异的原因分析

两个项目对"支持 2K1000"的理解深度不同：

**Chronix** 更多是在 QEMU LoongArch 上完善内核功能，2K1000 的适配是"尽力而为"的附加目标。其架构设计（DT 驱动、HAL 分层、完整中断控制器）具有更高的长期维护价值，但在真实上板的细节（UART 地址、非对齐处理、SATA vs MMC 选型）上存在明显缺失。

**rustoswhu** 的团队（尤其是主要负责人唐诗浩）实际完成了 2K1000 上板，代码中多处 `//2k1000` 注释和专门的 git commit 记录（`e57cf14`）表明这是真刀真枪踩坑后的修复，而非理论推断。代码更"土"，架构更简单，但关键路径上的正确性有实际验证。

### 10.3 对 rcore-lab 的参考价值

从两个项目的经验中，我们可以得出以下对自己的 rcore-lab 在 LoongArch/2K1000 适配上的参考：

1. **UART 地址**：2K1000 Vision5 的实际串口地址是 `0x1fe20000`（rustoswhu 已验证），必须走 `0x8000` DMW0 UC 窗口，完整虚拟地址 `0x800000001fe20000`

2. **非对齐处理是必做项**：上板必须添加 `-Ctarget-feature=-ual` 以及 `AddressNotAligned` 陷入处理，否则几乎所有用户程序都会崩溃

3. **PTE 必须设置 V + P + MAT**：三个位缺一不可，2K1000 MMU 对此严格验证

4. **存储是 SATA，不是 SD/MMC**：2K1000 Vision5 用 SATA 硬盘，需要 AHCI 驱动（PCI 扫描），文件系统通过 TFTP 分块传输 + uboot scsi write 烧录

5. **中断若需要，使用 EXTIOI + LS7A 硬编码**：DT 解析在 2K1000 上不稳定，onsite 阶段直接硬编码 `0x8000_0000_1000_0000` 更可靠

6. **禁用 LSX/LASX**：添加 `-Ctarget-feature=-lsx,-lasx` 防止 LLVM 生成 2K1000 上不支持的 LASX 指令

7. **所有 MMIO 访问走 `0x8000` 前缀**：包括 PCI 配置空间（`0x8000_00FE_0000_0000`）和 AHCI BAR 地址
