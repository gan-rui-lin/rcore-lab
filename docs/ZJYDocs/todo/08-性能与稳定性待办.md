# 性能与稳定性待办事项

**日期**: 2026/06/04

---

## 1. EPOLL_REGISTRY 内存泄漏

**现状**: `syscall/fs.rs` 中的 `EPOLL_REGISTRY: BTreeMap<(pid, fd), Arc<EpollFile>>` 在 `epoll_create1` 时插入，但在进程退出或 fd 关闭时**从未清理**。

**影响**: 长时间运行会导致内存持续增长。

**修复方案**:
- [ ] 在 `sys_close` 中检查关闭的 fd 是否是 epoll fd，如果是则调用 `epoll_unregister`
- [ ] 在进程退出时清理该 pid 的所有 epoll 注册
- [ ] 或者改用 per-process 的 epoll 列表，而不是全局 registry

---

## 2. POSIX_TIMERS 全局锁死锁风险

**现状**: `POSIX_TIMERS` 使用 `UPIntrFreeCell`（关中断互斥锁）。`check_posix_timers` 在 timer 中断上下文中调用，同时用户态 `timer_settime` 等也会获取该锁。

**风险**: `UPIntrFreeCell` 在获取时会关中断，所以理论上不会死锁。但如果有嵌套获取（如 timer 中断中获取锁时，该 CPU 上已经持有该锁），会 panic。

**修复方案**:
- [ ] 使用 `try_exclusive_access()` 在 timer 中断中尝试获取锁，失败则跳过本轮检查
- [ ] 或迁移到 per-process timer 存储

---

## 3. eventfd/signalfd 阻塞实现

**现状**: eventfd 和 signalfd 的阻塞 read 使用 `suspend_current_and_run_next()` 忙等循环。

**影响**: 浪费 CPU 时间，增加调度开销。

**优化方案**:
- [ ] 使用 waker/条件变量模式：将等待任务加入 wait queue，在 write/信号到达时唤醒
- [ ] 参考 pipe 的阻塞实现方式

---

## 4. epoll busy-poll 性能

**现状**: `sys_epoll_pwait` 使用 busy-poll（循环 poll 所有注册 fd + yield），与 `sys_ppoll` 风格一致。

**影响**: 大量注册 fd 时性能差。

**优化方案（低优先级）**:
- [ ] 实现 edge-trigger 模式下的事件缓存
- [ ] 使用 waker 机制在 fd 状态变化时主动唤醒 epoll 等待者

---

## 5. sdcard 镜像损坏风险

**现状**: `clock_settime` 系列测试会修改系统时间到 2038 年，如果测试中途被杀，文件系统的时间戳会被设为未来时间，可能导致 ext4 `needs journal recovery` 或挂载失败。

**已观察到**: round7 尝试启动时 `ext4_mount: rc = 95` 失败，需要从 xz 备份恢复。

**防护方案**:
- [ ] `clock_settime` 保持在 skip list 中，避免修改系统时间
- [ ] 在内核中限制 `clock_settime` 的时间范围（不允许设置到 2030 年以后）
- [ ] 在 initcode 开头添加 fsck 或挂载后检查

---

## 6. copy_file_range 简化实现

**现状**: `sys_copy_file_range` 只支持有 `read_at_kernel` 方法的文件（基于 offset 的内核读），不支持无 offset 的流式读。

**待办**:
- [ ] 支持 dst 侧的写入（目前只更新了 src offset，没有真正写到 dst）
- [ ] 使用 pipe 做中转或直接在内核空间 bounce buffer
