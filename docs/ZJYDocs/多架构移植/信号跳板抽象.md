# 多架构移植：信号跳板如何屏蔽架构差异

## 一、问题域：为什么信号处理需要跳板

当内核向用户态进程投递信号时，需要：

1. 保存当前 trap 上下文
2. 将 PC 修改为用户注册的信号 handler 地址
3. 将 RA（返回地址）修改为**信号跳板**地址
4. 返回用户态执行 handler
5. handler 返回时，RA 将 PC 导向信号跳板
6. 信号跳板执行 `sigreturn` 系统调用
7. 内核恢复之前保存的上下文

```
用户程序执行 ──→ 内核投递信号 ──→ 用户 signal handler
                                      │
                                      ▼ (handler 返回)
                                 信号跳板 (_sigreturn)
                                      │ li a7, 139
                                      │ ecall
                                      ▼
                                 内核 sys_sigreturn
                                      │ 恢复原上下文
                                      ▼
                                 用户程序继续执行
```

**架构差异在于**：跳板中的汇编指令（系统调用号、调用指令）完全不同。

## 二、抽象层设计

### 2.1 统一的 SIG_RETURN_ADDR 常量

每个架构在 `consts.rs` 中定义信号跳板的虚拟地址：

| 架构 | SIG_RETURN_ADDR | 说明 |
|------|----------------|------|
| RISC-V | `0xFFFF_FFC1_0000_0000` | 高半地址空间 |
| x86-64 | `0xFFFF_FF80_0000_0000` | x86 高半 |
| AArch64 | `0xFFFF_1000_0000_0000` | ARM 高半 |
| LoongArch | `0x40_0000_0000` | DMW 地址空间 |

内核代码只使用 `SIG_RETURN_ADDR`，不关心具体值。

### 2.2 每架构实现 sigtrx.rs

每个架构在自己目录下提供 `sigtrx.rs` 模块，包含：
- `_sigreturn()` 函数：包含执行 sigreturn 系统调用的汇编
- `init()` 函数：建立页表映射
- `get_trx_mapping()` 函数：返回映射的物理地址

## 三、各架构信号跳板实现

### 3.1 RISC-V 64

```rust
// arch/src/riscv64/page_table/sigtrx.rs

#[naked]
#[link_section = ".sigtrx.sigreturn"]
unsafe extern "C" fn _sigreturn() -> ! {
    core::arch::asm!(
        "li  a7, 139",    // sys_rt_sigreturn 调用号
        "ecall",          // RISC-V 系统调用指令
        options(noreturn)
    )
}
```

**系统调用 ABI**：将调用号 139 放入 a7 (x17)，执行 ecall。

**页表映射**：使用两级页表（TRX_STEP1 + TRX_STEP2）将 `_sigreturn` 函数映射到 `SIG_RETURN_ADDR`：

```rust
static mut TRX_STEP1: [PTE; 512] = [PTE(0); 512];  // 末级页表
static mut TRX_STEP2: [PTE; 512] = [PTE(0); 512];  // 中间页表

pub fn init() {
    unsafe {
        // 末级：映射 _sigreturn 的物理页，权限 ADUVRX（用户可读可执行）
        TRX_STEP1[0] = PTE::from_addr(
            _sigreturn as usize & !VIRT_ADDR_START,
            PTEFlags::ADUVRX.union(PTEFlags::G)
        );
        // 中间级：指向末级页表
        TRX_STEP2[0] = PTE::from_addr(
            TRX_STEP1.as_ptr() as usize & !VIRT_ADDR_START,
            PTEFlags::V
        );
    }
}
```

在每个新创建的页表中，`restore()` 将信号跳板挂到根页表的固定位置：

```rust
// sv39.rs 中的 restore()
arr[0x104] = PTE::from_addr(get_trx_mapping(), PTEFlags::V);
```

### 3.2 x86-64

```rust
// arch/src/x86_64/sigtrx.rs

#[naked]
#[link_section = ".sigtrx.sigreturn"]
unsafe extern "C" fn _sigreturn() -> ! {
    core::arch::asm!(
        "mov  rax, 15",    // x86-64 的 sys_rt_sigreturn 调用号是 15
        "syscall",         // x86-64 系统调用指令
        options(noreturn)
    )
}
```

**注意**：x86-64 的 sigreturn 调用号是 **15**，不是 139。这是 Linux x86-64 ABI 的规定。

**页表映射**：
```rust
static mut TRX_STEP1: PD = [PDEntry(0); 512];   // Page Directory
static mut TRX_STEP2: PT = [PTEntry(0); 512];   // Page Table

pub fn init() {
    unsafe {
        TRX_STEP1[0] = PDEntry::new(
            (TRX_STEP2.as_ptr() as usize & !VIRT_ADDR_START).into(),
            PDFlags::P | PDFlags::RW
        );
        TRX_STEP2[0] = PTEntry::new(
            (_sigreturn as usize & !VIRT_ADDR_START).into(),
            PTFlags::P | PTFlags::US    // Present + User 可访问
        );
    }
}
```

### 3.3 LoongArch64

```rust
// arch/src/loongarch64/sigtrx.rs

#[naked]
#[link_section = ".sigtrx.sigreturn"]
unsafe extern "C" fn _sigreturn() -> ! {
    core::arch::asm!(
        "li.d  $a7, 139",    // 调用号 139
        "syscall  0",        // LoongArch 系统调用指令
        options(noreturn)
    )
}
```

**页表映射**：
```rust
static mut TRX_STEP: [[PTE; 512]; 2] = [[PTE(0); 512]; 2];

pub fn init() {
    unsafe {
        // TRX_STEP[0][0]：末级，映射 _sigreturn 物理页
        TRX_STEP[0][0] = PTE::from_addr(
            PhysAddr(_sigreturn as usize & !VIRT_ADDR_START),
            MappingFlags::URX.into()     // User + Read + Execute
        );
        // TRX_STEP[1][0]：中间级，指向末级
        TRX_STEP[1][0] = PTE(TRX_STEP.as_ptr() as usize & !VIRT_ADDR_START);
    }
}
```

### 3.4 AArch64

目前 rustoswhu 的 AArch64 信号跳板**尚未完整实现**。如果实现，预期代码为：

```rust
// 预期的 arch/src/aarch64/sigtrx.rs
#[naked]

unsafe extern "C" fn _sigreturn() -> ! {
    core::arch::asm!(
        "mov  x8, 139",     // 调用号 139 放入 x8
        "svc  #0",          // AArch64 系统调用指令

```

## 四、链接脚本集成

所有架构的链接脚本中都有相同的段定义：

```ld
.sigtrx ALIGN(4K): {
    *(.sigtrx .sigtrx.*)
}
```

这确保：
- 信号跳板代码被放在独立的 4KB 对齐段中
- 可以被精确地映射为一个物理页
- `#[link_section = ".sigtrx.sigreturn"]` 属性确保函数放在正确位置

## 五、内核侧信号投递（架构无关）

在 `os/src/task/mod.rs` 中，信号投递使用统一的 `TrapFrameArgs` 和 `SIG_RETURN_ADDR`：

```rust
fn call_user_signal_handler(/* ... */) {
    // 1. 备份当前 trap 上下文
    task_inner.trap_ctx_backup = Some(trap_ctx.clone());

    // 2. 设置 handler 地址（架构无关）
    trap_ctx[TrapFrameArgs::SEPC] = handler;

    // 3. 设置返回地址为信号跳板（架构无关）
    trap_ctx[TrapFrameArgs::RA] = if flags.contains(SigActionFlags::RESTORER) {
        sig_action.restore    // 用户自定义 restorer
    } else {
        SIG_RETURN_ADDR       // 默认跳板
    };

    // 4. 传递信号号作为参数（架构无关）
    trap_ctx[TrapFrameArgs::ARG0] = sig as usize;

    // 5. 设置信号掩码
    task_inner.signal_mask = sig_action.mask;
}
```

这段代码完全不涉及任何架构细节——通过 `TrapFrameArgs` 枚举和 `SIG_RETURN_ADDR` 常量，内核以统一方式完成信号投递。

## 六、sigreturn 系统调用号差异

这是一个容易被忽略的差异：

| 架构 | sys_rt_sigreturn 调用号 | 原因 |
|------|----------------------|------|
| RISC-V | 139 | Linux RISC-V ABI |
| x86-64 | **15** | Linux x86-64 ABI（历史原因不同） |
| AArch64 | 139 | Linux AArch64 ABI |
| LoongArch | 139 | Linux LoongArch ABI |

x86-64 使用不同的调用号是因为 Linux 的系统调用号表是按架构独立编号的。大多数架构使用通用编号（从 `include/uapi/asm-generic/unistd.h`），但 x86-64 沿用了自己的历史编号。

## 七、SigAction 结构体的布局差异

即使在信号投递的通用逻辑之下，`SigAction` 结构体的字段顺序在不同架构上也有区别：

**RISC-V / x86-64**：
```rust
#[repr(C)]
pub struct SigAction {
    pub handler: usize,
    pub flags: SigActionFlags,
    pub restore: usize,        // restorer 在 flags 后面
    pub mask: SignalFlags,
}
```

**LoongArch64**：
```rust
#[repr(C)]
pub struct SigAction {
    pub handler: usize,
    pub flags: SigActionFlags,
    pub mask: SignalFlags,      // mask 和 restore 顺序互换！
    pub restore: usize,
}
```

这个差异需要在定义 SigAction 时使用 `#[cfg(target_arch)]` 处理。

## 八、与 rcore-lab 的对比

rcore-lab 当前的信号跳板是直接硬编码 RISC-V 指令的。

**改造要点**：
1. 将 `_sigreturn` 函数移到 `arch/src/riscv64/sigtrx.rs`
2. 每个架构实现自己的 `_sigreturn`（不同调用号、不同指令）
3. `SIG_RETURN_ADDR` 改为从 `arch::consts` 导入
4. 信号投递代码（`call_user_signal_handler`）使用 `TrapFrameArgs` 而非直接字段访问
5. 注意处理 `SigAction` 字段顺序的架构差异
