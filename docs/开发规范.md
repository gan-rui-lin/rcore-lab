## 1. 分支管理

### 分支模型

```
master (稳定分支，评测提交用)
  └── dev (开发集成分支)
        ├── feature/xxx   (功能开发)
        ├── fix/xxx       (Bug 修复)
        └── test/xxx      (测试点调试)
```

### 分支规则

| 分支 | 用途 | 谁可以 merge | 保护级别 |
|------|------|-------------|---------|
| `master` | 稳定版本，评测系统使用 | 确认无回归后从 dev merge | 受保护，禁止直接 push |
| `dev` | 开发集成，日常测试 | 功能分支完成后 merge 到此 | 允许 push |
| `feature/*`, `fix/*`, `test/*` | 具体功能/修复/测试点 | 开发者自由操作 | 无保护 |

### 工作流程

```bash
# 1. 从 dev 签出新分支
git checkout dev
git pull origin dev
git checkout -b feature/loongarch-uart

# 2. 开发、提交
git add -A && git commit -m "feat(driver): LoongArch UART 驱动"

# 3. 提测：merge 回 dev
git checkout dev
git merge feature/loongarch-uart
git push origin dev

# 4. 评测通过后：merge 到 master
git checkout master
git merge dev
git push origin master
git push commit master   # GitLab 评测仓库
```

### 命名规范

- **功能分支**: `feature/xxx`，如 `feature/loongarch-net`、`feature/glibc-dynamic`
- **修复分支**: `fix/xxx`，如 `fix/tcp-crr-timeout`、`fix/mmap-ghost-pte`
- **测试分支**: `test/xxx`，如 `test/lmbench-signal`、`test/iperf-parallel`

### Commit Message 格式

```
<类型>(<模块>): <简短描述>

<可选的详细说明>

类型:
  feat     新功能
  fix      Bug 修复
  docs     文档
  refactor 重构（不改变功能）
  test     测试相关
  wip      进行中的工作

模块:
  net      网络模块
  mm       内存管理
  fs       文件系统
  signal   信号处理
  task     进程/线程
  user     用户态 (initcode 等)
  la       LoongArch 架构特定
  rv       RISC-V 架构特定
```

## 2. 构建与运行

### 基本命令

```bash
# === RISC-V ===
make rv                                    # 编译 RV 内核
bash run.sh -f sdcard-rv.img -t all        # 运行（默认 RV）

# === LoongArch ===
make la                                    # 编译 LA 内核
bash run-la.sh -f sdcard-la.img -t la      # 运行 LA

# === 指定测试套件 ===
SINGLE_TEST=musl-iperf LOG=ERROR bash run.sh -f sdcard-rv.img -t all
SINGLE_TEST=glibc-netperf LOG=ERROR bash run-la.sh -f sdcard-la.img -t la

# === 清理 ===
make clean                                 # 清理所有构建产物
```

### SINGLE_TEST 参数说明

`SINGLE_TEST` 是编译期环境变量（`option_env!`），控制 initcode 运行哪些测试：

| 值 | 行为 |
|----|------|
| `musl-iperf` | 只跑 `/musl/iperf_testcode.sh` |
| `glibc-netperf` | 只跑 `/glibc/netperf_testcode.sh` |
| `iperf` | 先跑 musl iperf，再跑 glibc iperf |
| `netperf` | 先跑 musl netperf，再跑 glibc netperf |
| `musl` | 跑 musl 下所有测试套件 |
| `glibc` | 跑 glibc 下所有测试套件 |
| `all` | 跑所有 libc × 所有套件 |
| 不设置 | 由 `ENABLE_ALL_TESTS` 和 `TEST_SUITES` 决定 |
| `/musl/busybox` | 直接运行指定路径的二进制 |

**注意**：`SINGLE_TEST` 在编译期通过 `option_env!` 嵌入 initcode。修改后必须重新编译：

```bash
# 方法 1：touch initcode 源文件强制重编译
touch os/src/task/initcode.rs        # RV
touch os/src/task/initproc_embed_loongarch64.rs  # LA

# 方法 2：make clean 后重编
make clean && SINGLE_TEST=musl-iperf make rv
```

### initcode.rs 关键配置

```rust
// user/src/bin/initcode.rs

// 总开关：不设 SINGLE_TEST 时是否跑所有测试
const ENABLE_ALL_TESTS: bool = true;

// 测试套件列表（远端评测时可精简为需要的项）
const TEST_SUITES: [&str; 11] = [
    "basic", "busybox", "cyclictest", "iozone", "iperf",
    "libcbench", "libctest", "lmbench", "ltp", "lua", "netperf",
];

// libc 变体
const TEST_LIBC_ROOTS: [&str; 2] = ["/musl", "/glibc"];
```

**远端评测**时，可以注释掉不需要的套件来节省评测时间：

```rust
const TEST_SUITES: [&str; 2] = [
    "iperf",
    "netperf",
];
```

修改 `TEST_SUITES` 数组大小时，记得同步修改泛型参数（如 `[&str; 11]` → `[&str; 2]`）。

### LOG 日志级别

```bash
LOG=ERROR   # 只输出错误（推荐日常测试）
LOG=WARN    # 错误 + 警告（看信号/异常）
LOG=INFO    # 包含 syscall 摘要
LOG=SYSCALL # 详细 syscall 跟踪（调试用）
LOG=TRACE   # 全量日志（巨大，慎用）
```

**调试建议**：先用 `LOG=ERROR` 跑一遍看结果，再用 `LOG=WARN` 看异常，最后需要时用 `LOG=SYSCALL` 精确定位。

## 3. 调试方法

### 3.1 日志调试（最常用）

```bash
# 跑测试并保存日志
LOG=WARN SINGLE_TEST=glibc-netperf bash run-la.sh -f sdcard-la.img -t la > debug01.log 2>&1

# 搜索关键信息
rg "signum = 4" debug01.log          # IllegalInstruction
rg "signum = 12" debug01.log         # StorePageFault
rg "SIGKILL|Panicked|bad addr" debug01.log
rg "ret=-" debug01.log | head -20    # syscall 负返回值
```

### 3.2 关键日志模式

| 模式 | 含义 | 处理 |
|------|------|------|
| `signum = 4` | IllegalInstruction | 检查 sepc 处的指令，可能是架构不支持或 PTE 权限 |
| `signum = 12` | StorePageFault | 检查 stval 地址，可能是 COW/mmap 映射问题 |
| `signum = 15` | PageLoadFault | 同上 |
| `[ERROR]` | 内核错误 | 通常是文件系统或资源不足 |
| `ret=-` (syscall) | syscall 返回错误 | 对照 errno 表排查 |
| `FUTEX_WAIT val=N` | 进程阻塞在 futex | N≠0 且单线程 → BSS 未清零 |
| `symbol lookup error` | 动态链接失败 | 检查 /lib/ /lib64/ 下是否有对应 .so |

### 3.3 sdcard 镜像操作

```bash
# 解压镜像（QEMU 运行后镜像会被修改，每次测试前解压）
xz -dkf sdcard-rv.img.xz
xz -dkf sdcard-la.img.xz

# 挂载镜像查看内容（macOS 用 Docker）
IMAGE_FILE=sdcard-la.img ./ext4-tools.sh shell
# 或直接用 docker
docker run --rm --privileged \
  -v "$(pwd)/sdcard-la.img:/workspace/sdcard.img" \
  rcore-ext4:latest \
  bash -c "e2fsck -y /workspace/sdcard.img && mount -o loop /workspace/sdcard.img /mnt/sdcard && ls /mnt/sdcard/musl/"
```

**本地评分**：

```bash
JUDGE=../../autotest-for-oskernel/kernel/judge

# 评分（stdin 传入 QEMU 输出日志）
python3 $JUDGE/judge_iperf-musl.py < test.log
python3 $JUDGE/judge_netperf-glibc.py < test.log

# RV QEMU 输出带 \r，本地 judge 正则可能不匹配
# 远端评测系统不受影响。本地可用 tr 去除：
tr -d '\r' < test.log | python3 $JUDGE/judge_iperf-musl.py
```

**judge 脚本工作原理**：解析 QEMU 串口输出，通过正则匹配 `====== iperf BASIC_UDP begin ======` 等标记提取测试数据，与 baseline 对比计算得分。每项满分 2.0，公式为 `score = 2 - baseline/result`（result > baseline 时）或 `1.0`（result < baseline 时）。

## 4. 架构差异速查

| 项目 | RISC-V | LoongArch |
|------|--------|-----------|
| QEMU | `qemu-system-riscv64 -machine virt` | `qemu-system-loongarch64` |
| VirtIO 网卡 | `virtio-net-device` (MMIO) | `virtio-net-pci` (PCI) |
| VirtIO 块设备 | `virtio-blk-device,bus=virtio-mmio-bus.0` | `virtio-blk-pci` |
| 内存 | 128M | 4G |
| glibc ld.so | `/lib/ld-linux-riscv64-lp64d.so.1` | `/lib64/ld-linux-loongarch-lp64d.so.1` |
| glibc 库搜索路径 | `/lib/` | `/lib64/` |
| musl ld.so | `/lib/ld-musl-riscv64-sf.so.1` | `/lib64/ld-musl-loongarch-lp64d.so.1` |
| 中断使能寄存器 | `sstatus.SIE`（写入立即生效） | `crmd.IE`（立即），`prmd.PIE`（仅 ertn 恢复） |
| 编译 initcode | `touch os/src/task/initcode.rs` | `touch os/src/task/initproc_embed_loongarch64.rs` |
| sdcard 文件名 | `libc.so` / `libm.so`（无 .6） | `libc.so.6` / `libm.so.6` |

## 5. 常见问题

### Q: 修改了 SINGLE_TEST 但测试没变？
A: `SINGLE_TEST` 是编译期变量。必须 `touch` 对应 initcode 源文件或 `make clean` 后重编译。

### Q: glibc 动态链接程序报 `cannot open shared library`？
A: 检查 `os/src/fs/mod.rs` 的 `ensure_busybox_links()`，确认对应架构的 `libc.so.6`/`libm.so.6` 有 hardlink 到 `/lib/` 或 `/lib64/`。

### Q: 测试卡在 `FUTEX_WAIT val=2`？
A: BSS 未清零。检查 `os/src/mm/memory_set.rs` 的 `map_one()` 是否有 `ppn.get_bytes_array().fill(0)`。

### Q: `SINGLE_TEST=iperf` 跑完 musl 后 glibc 不开始？
A: daemon 进程（iperf3 -s -D）残留占端口。`reap_orphans()` 需要用 `waitpid_nohang`（WNOHANG）非阻塞 reap。

### Q: LoongArch 定时器中断不触发？
A: 检查 `crmd.IE` 而非 `prmd.PIE`。LoongArch 的 `prmd.PIE` 仅在 `ertn` 恢复时生效，不影响当前中断。

### Q: MAP_FIXED mmap 后页面数据不对？
A: 检查 `unmap_range` 是否正确清理了部分重叠区域的"幽灵 PTE"。参考 `LoongArch-glibc动态链接netperf全通过修复.md`。
