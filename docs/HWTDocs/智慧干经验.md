## 1. 先回答“从哪里开始”：源码与日志分别去哪找

很多调试慢，不是技术难，而是第一步就找错路径。

### 1.1 内核实现源码（你要改的代码）

- syscall 分发与实现：
  - `os/src/syscall/mod.rs`
  - `os/src/syscall/process.rs`
  - `os/src/syscall/fs.rs`
  - `os/src/syscall/net.rs`（若有网络分发）
- futex / 任务：
  - `os/src/task/futex.rs`
  - `os/src/task/process.rs`
- procfs：
  - `os/src/fs/vfs/procfs.rs`
- 网络 socket 细节：
  - `os/src/net/syscall.rs`
  - `os/src/net/unix_socket.rs`

### 1.2 LTP 测试源码（你要理解“它到底在测什么”）

优先路径（本机已有）：

- `testsuits-for-oskernel/ltp-full-20240524/testcases/kernel/syscalls/...`

例如：

- futex: `.../futex/futex_wake02.c`, `.../futex/futex_wait03.c`
- clock_nanosleep: `.../clock_nanosleep/clock_nanosleep01.c`
- clone: `.../clone/clone07.c`

### 1.3 运行镜像里实际二进制位置

`initcode.rs` 里跑的是镜像内程序，不是你源码树里的可执行文件。常见路径：

- `/musl/ltp/testcases/bin/*` 或 `/musl/ltp-full/testcases/bin/*`

如需核对 SD 卡内容，挂载后查看：

```bash
sudo mount -o loop sdcard-rv.img /mnt/sdcard-2025
```

## 2. 不要盲跑 all：如何“单调一小部分”快速复现

调试最忌讳：每轮全量跑 `-t all`，一轮几十分钟，且噪声巨大。

### 2.1 单测优先策略

优先级建议：

1. 单个失败用例（最快）
2. 小问题集（比如 `tmp-ltp-stuck`）
3. 再扩大到 `tmp-ltp`
4. 最后才全量

### 2.2 常用执行模板

单问题：

```bash
SINGLE_TEST=tmp-ltp-stuck LOG=INFO timeout 60 bash run.sh -f sdcard-rv.img > allrv_ltp-stuck_INFO.log
```

如果你要针对某个程序名追踪：

```bash
TRACE_NAME=futex_wake02 LOG=TRACE SINGLE_TEST=tmp-ltp-stuck timeout 60 bash run.sh -f sdcard-rv.img > trace.log
```

### 2.3 timeout 怎么设才合理

推荐分层：

- **30~60s**：日常迭代（快速失败/快速验证）
- **120~180s**：怀疑性能慢而非死锁时
- **300s**：只在确认“测试本身就是长跑”时使用

经验：能用 60s 定位的，不要开 300s。
大 timeout 会掩盖“本应立即返回 errno 的语义 bug”。

## 3. 日志怎么读：从“症状”反推“根因”而不是猜

## 3.1 第一轮先做失败分类，而不是逐条看

```bash
rg "TBROK|TFAIL" "Riscv输出 (16).txt"
```

按类别聚合：

- ENOSYS（未实现 syscall）
- ENOENT（/proc 节点缺失）
- EINTR/EFAULT/EINVAL（语义不准）
- timeout（可能卡死链路）

这一步能立刻看出“该优先修哪一类”。

## 3.2 第二轮抓“关键危险信号”

```bash
rg "signum = 4|signum = 12|trap_handler: Exception|\\[ERROR\\]|bad addr|Panicked|sepc|stval" all*.log
```

说明：

- `signum=4` / `signum=12`：通常是非法指令/页故障，优先修稳定性
- `sepc/stval`：直接给你 fault 指令地址和坏地址，能快速映射到路径

## 3.3 第三轮看“第一个不符合预期的 errno”

LTP 常常是“故意喂错参数”，期待特定 errno。
你要找的是第一个偏差点，而不是最后 TBROK 那一行。

例如：

- 测试预期 `EINVAL`，结果卡 30 秒超时 -> 通常是参数校验缺失
- 测试预期 `EFAULT`，结果 `EINTR` -> 通常是错误优先级处理错

## 4. 如何与 Linux 行为对齐（这是最关键的一步）

“看起来能跑”不等于“通过 LTP”。
必须和 Linux 的 **返回值/errno/时序语义** 对齐。

## 4.1 对齐方法（建议固定流程）

1. 打开对应 LTP 用例源码，写下它的预期：
   - 调哪个 syscall
   - 传了哪些边界参数
   - 期待什么 errno/状态
2. 对照 man page / Linux 语义（尤其 errno）
3. 在内核 syscall 入口与错误返回点打日志
4. 证明“偏差发生在哪个条件分支”

## 4.2 参考仓库对齐（你提到的做法）

可借鉴路径：

- `T202410487992457-1800`

建议不是“整段抄代码”，而是对齐以下三个点：

1. 分支判定顺序（先判什么）
2. errno 优先级（EFAULT vs EINTR vs EINVAL）
3. 信号/重启策略（SA_RESTART、SIGALRM 的处理）

对齐的是“行为”，不是“实现细节”。

## 5. 典型问题如何快速定位（实战模板）

## 5.1 futex 类卡住

**症状**：wake 数量异常、线程永远不醒。
**第一反应**：看 wait/wake 是否用了同一个 key。

建议临时日志：

- pid/tid
- uaddr
- private/shared 标志
- key（必要时打印 VA 和 PA）

如果同 uaddr 的 wait/wake key 不一致，优先查：

- private futex 是否错误使用 PA
- COW 后 PA 漂移
- requeue 路径是否沿用同一 key 规则

## 5.2 /proc 观察链路卡住

**症状**：`TST_PROCESS_STATE_WAIT` 一直不结束。
**第一反应**：不是先怀疑调度，而是先查 `/proc` 文件是否存在且语义正确。

重点检查：

- `/proc/<pid>/stat`
- `/proc/<pid>/task/<tid>/stat`

很多用例依赖这些节点做“测试流程控制”，缺失会无限轮询。

## 5.3 clock_nanosleep / time 类超时

**症状**：本应立即失败却长睡眠。
**第一反应**：参数校验缺失（tv_nsec/flags/clock_id）。

排查顺序：

1. `tv_nsec` 边界是否严格检查
2. `clock_id` 是否支持且返回码准确
3. 被信号中断时 rem 回写失败是否返回 EFAULT

## 6. 怎样加日志最省时间（避免日志洪水）

日志不是越多越好，关键是“足够证明假设”。

推荐只在四类点打日志：

1. syscall 入口参数（一次）
2. 关键状态转移（阻塞/唤醒/回收）
3. 错误返回分支（return errno 前）
4. 地址翻译点（VA/PA，仅当怀疑映射问题）

并且强烈建议按测试名过滤（例如只对 `futex_wake02` 打）：

```rust
if proc_name == "futex_wake02" {
    info!(...);
}
```

这样 `LOG=INFO` 就足够，不必全程 TRACE。

## 7. “快而稳”的完整调试闭环（建议团队统一）

## Step A：建立最小复现

- 固定单测或小集合
- 固定 timeout（先 60s）
- 固定日志级别（先 INFO）

## Step B：先看测试源码再改内核

至少明确三件事：

1. 它期望什么返回值
2. 它如何判断 pass/fail
3. 它是否依赖 `/proc` / 信号 / 子进程状态

## Step C：证据驱动改动

- 每次只改一类语义
- 每次只验证一个假设
- 改完立刻回归该单测

## Step D：扩大回归范围

单测过后，跑问题集；问题集过后，再跑更大集合。
不要一开始就 all。

## Step E：清理临时日志并沉淀文档

- 删除临时 debug 输出
- 在 GRLDocs 写“如何判断出根因”的逻辑链


```bash

```

## 9. 最后给同事的三条“避坑建议”

1. **先看测试源码，再看内核源码**。你先知道“对方怎么判你错”，才知道改哪里。
2. **先对齐语义，再谈性能和重构**。LTP 对 errno 和时序非常敏感，不对齐就一直 TBROK/TFAIL。
3. **先小闭环，再大回归**。
   单测 5 分钟出结论，比 all 跑 40 分钟更有价值。

---

## 10. 结语

LTP 调试本质上不是“拼命跑测试”，而是“建立可验证的语义对齐流程”。
只要团队统一：**路径正确（源码/日志）+ 方法正确（单测/timeout）+ 判断正确（证据链）**，调试效率会明显提升，且修复更稳、更可复用。
