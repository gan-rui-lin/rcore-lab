# 三内核用户虚拟地址布局对比分析

**日期**: 2026/04/05

本文档对比分析 rcore-lab、OSKernel2025-rustoswhu 和 oskernel2025-chronix-retest 三个内核实现的用户虚拟地址空间设计，并探讨 musl/glibc 的 mmap 使用方式及其与内核地址布局的协作关系。

---

## 一、关键地址常量对比

### 1.1 USER_MMAP_TOP

| 仓库 | USER_MMAP_TOP | 换算大小 | 备注 |
|------|---------------|----------|------|
| **rcore-lab** | `0x6_0000_0000` | 24 GB | 固定值，mmap 从此向高地址分配 |
| **rustoswhu** | `0x11_0000_0000` (config crate) <br> `0x6000_0000` (os/src/config.rs) | 68 GB / 1.5 GB | 存在两处定义，实际使用 config crate 的 68GB |
| **chronix** | `USER_FILE_END` ≈ `USER_STACK_BOTTOM - PAGE_SIZE` | 动态计算 | RV64: ≈ 240 GB <br> LA64: ≈ 128 TB - 16MB |

**计算方式**（chronix RISC-V 64）：
```
USER_ADDR_SPACE.end = 0x0000_0040_0000_0000 (256 GB)
USER_STACK_TOP = 256GB - 4KB = 0x3F_FFFF_F000
USER_STACK_SIZE = 16 MB (4096 * 4096)
USER_STACK_BOTTOM = USER_STACK_TOP - 16MB ≈ 0x3F_FF00_0000
USER_FILE_END = USER_STACK_BOTTOM - 4KB ≈ 0x3F_FF00_0000 (~240 GB)
```

---

### 1.2 heap_bottom（堆底地址）

| 仓库 | heap_bottom 计算方式 | 典型值范围 |
|------|---------------------|------------|
| **rcore-lab** | ELF 所有 LOAD 段结束后的 `max_end_va` | 静态链接: ~4MB <br> PIE+interp: ~0x4010_0000 (1GB+) |
| **rustoswhu** | 同 rcore-lab，紧随 ELF 段结束 | 与 rcore-lab 类似 |
| **chronix** | `ret.brk = max_end_vpn.start_addr()` | 与 ELF 段结束对齐 |

**heap_bottom 的最大可能值**：

理论上 heap 可以增长到与 mmap 区域相接触。假设 mmap 区域不使用：

| 仓库 | 理论最大 heap 范围 |
|------|-------------------|
| **rcore-lab** | heap_bottom → USER_MMAP_TOP (24GB) 之间 |
| **rustoswhu** | heap_bottom → USER_MMAP_TOP (68GB) 之间 |
| **chronix** | heap_bottom → brk 增长到 USER_FILE_BEG 之前 |

**实际场景示例**（rcore-lab LoongArch musl busybox）：
```
heap_bottom ≈ 0x1201fe000 (~4.5GB，因 PIE 加载偏移)
```

---

### 1.3 vload_base（ELF/PIE 加载基址）

| 仓库 | 加载基址策略 | 值 |
|------|-------------|-----|
| **rcore-lab** | ET_DYN + min_vaddr=0 → 偏移 | `0x4000_0000` (1GB) |
| **rustoswhu** | 未找到明确定义 | 未显式设定 |
| **chronix** | DL_INTERP_OFFSET 用于解释器 | `0x20_0000_0000` (128GB) |

**rcore-lab 详细策略**（`os/src/mm/memory_set.rs:706-770`）：

```rust
// PIE executables (SharedObject with interp, min_load_vaddr=0) need
// a non-zero load_base so they don't start at VA 0x0.
let load_base = if elf_type == SharedObject && min_load_vaddr == 0 {
    0x4000_0000usize  // 1GB offset
} else {
    0  // 静态链接按 ELF 指定地址
};
```

解释器（ld-linux.so）加载在主 ELF 段之后：
```rust
let mut interp_base = max_end_va.into();
interp_base = align_up(interp_base, PAGE_SIZE);
```

## 三、与 Linux 规范的符合程度对比

### 3.1 Linux x86_64 典型用户地址布局（参考）

```
高地址（47位寻址空间顶端）
┌──────────────────────────────────────────────┐
│   vsyscall / VDSO 区域                        │ 接近 0x7FFF_FFFF_F000
├──────────────────────────────────────────────┤
│   Stack (向下增长, RLIMIT_STACK)              │
├──────────────────────────────────────────────┤
│   mmap 区域 (从高向低分配)                    │ 典型: 接近栈底
│   - 共享库 (libc.so, ld-linux.so)            │
│   - 匿名 mmap                                │
│   - 文件 mmap                                │
├──────────────────────────────────────────────┤ mmap_base (ASLR 随机化)
│                  (空闲区)                     │
├──────────────────────────────────────────────┤ brk (heap 顶)
│              Heap (向上增长)                  │
├──────────────────────────────────────────────┤ end (ELF 结束)
│   BSS (未初始化数据)                          │
├──────────────────────────────────────────────┤
│   Data (已初始化数据)                         │
├──────────────────────────────────────────────┤
│   Text (代码段)                               │ 典型: 0x400000 或 PIE 随机
└──────────────────────────────────────────────┘ 0x0
```

### 3.2 符合度评估

| 特性 | Linux 行为 | rcore-lab | rustoswhu | chronix |
|------|-----------|-----------|-----------|---------|
| mmap 分配方向 | 向低地址（从栈附近向下） | **向高地址** ⚠️ | 未明确 | **向低地址** ✅ |
| PIE 基址 | ASLR 随机化，通常 0x55xxxxxx | 固定 0x4000_0000 | 未明确 | 固定 offset |
| 解释器位置 | mmap 区域（高地址） | 紧随主 ELF | DL_INTERP_OFFSET 固定 | 固定 0x20_0000_0000 |
| 栈-mmap 相邻 | 是，mmap 在栈下方 | 否，两者分离 | 否 | **是** ✅ |
| heap-ELF 连续 | 是，heap 紧随 BSS | **是** ✅ | **是** ✅ | **是** ✅ |
| ASLR 支持 | 是 | 否 | 否 | 否 |

### 3.3 结论：chronix 最符合 Linux 规范

**理由**：

1. **mmap 分配策略**：chronix 将 mmap 区域放在栈下方，并从 `USER_FILE_END`（栈底-4KB）向低地址分配，与 Linux 一致。rcore-lab 的 mmap 从 24GB 向高地址分配，与 Linux 相反。

2. **地址区域连续性**：chronix 的设计让栈→mmap→空闲→heap→ELF 形成连续的地址空间利用模式。

3. **分离的 file/share mmap 区域**：chronix 明确区分了文件 mmap 和共享 mmap，更接近 Linux 的 VMA 分类。

4. **用户地址空间上界**：chronix RISC-V 使用 `0x40_0000_0000`（256GB），合理地利用了 39 位虚拟地址空间的低 47% 部分。

## 四、musl 和 glibc 的 mmap 使用方式

### 4.1 mmap 的两大使用场景

#### 4.1.1 内存分配器（malloc 后端）

**glibc malloc (ptmalloc2)**:
```c
// 大块分配（>= MMAP_THRESHOLD，通常 128KB）
void* p = mmap(NULL, size, PROT_READ|PROT_WRITE, 
               MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
```
- addr=NULL 让内核选择地址
- Linux 内核从 `mm->mmap_base` 向下分配（接近栈底）

**musl malloc**:
```c
// 类似策略，但 musl 可能更积极使用 mmap
// LoongArch musl 特别会在堆区使用 guard page:
mmap(heap_bottom, 4KB, PROT_NONE, MAP_FIXED|MAP_PRIVATE|MAP_ANONYMOUS, -1, 0);
```

#### 4.1.2 共享库加载

动态链接器（ld-linux.so）加载共享库时：
```c
// 映射 .text/.rodata 段
mmap(NULL, text_size, PROT_READ|PROT_EXEC, 
     MAP_PRIVATE|MAP_DENYWRITE, fd, text_offset);

// 映射 .data/.bss 段  
mmap(data_addr, data_size, PROT_READ|PROT_WRITE,
     MAP_PRIVATE|MAP_FIXED|MAP_DENYWRITE, fd, data_offset);
```

### 4.2 为什么 musl/glibc 的 mmap 不会与其他区域冲突

#### 4.2.1 内核地址分配策略

Linux 内核 `arch_get_unmapped_area_topdown()` 实现：

```c
unsigned long addr = mm->mmap_base;  // 通常接近 TASK_SIZE - stack
// 向下搜索足够大的空闲区域
while (addr > len) {
    vma = find_vma(mm, addr - len);
    if (!vma || addr <= vma->vm_end)
        return addr - len;  // 找到！
    addr = vma->vm_start;   // 跳过已映射区域
}
```

**关键点**：
1. `addr=NULL` 时，内核负责找到合适地址
2. 从高地址向低地址搜索，自动避开栈、heap、已有 mmap
3. 返回的地址一定在当前 VMA 空洞中

#### 4.2.2 rcore-lab 的保护机制

rcore-lab 通过 `MapAreaType` 枚举保护关键区域：

```rust
pub enum MapAreaType {
    Heap,        // 受保护
    Stack,       // 受保护  
    ElfSegment,  // 受保护
    MmapAnon,    // 可被 munmap
    MmapFile,    // 可被 munmap
    // ...
}

pub fn unmap_range(&mut self, start_va: VirtAddr, end_va: VirtAddr) {
    for area in &self.areas {
        match area.area_type {
            MapAreaType::Heap | MapAreaType::Stack | MapAreaType::ElfSegment => {
                // 跳过，不允许 munmap
                continue;
            }
            _ => { /* 允许 unmap */ }
        }
    }
}
```

#### 4.2.3 地址布局设计的隔离

三个内核的设计都遵循一个核心原则：**关键区域之间留有足够空隙**

```
rcore-lab 间隙分析:
USER_STACK_TOP (32GB) 
    ↓ 8GB 空隙
USER_MMAP_TOP  (24GB)
    ↓ ~22GB 空隙（典型场景）
heap_bottom    (~2GB for PIE)
```

musl/glibc 请求 `mmap(NULL, ...)` 时，内核从 mmap_base 开始分配，绝不会"侵入"栈或 ELF 区域。

## 五、LoongArch musl 堆损坏问题分析

参见 `/home/grl/codeRepo/rcore-lab/docs/GRLDocs/LA-musl-heap-corruption-fix-2026-04-03.md`

### 5.1 问题根因

LoongArch musl 的 malloc 实现比 RISC-V 更激进地使用 `mmap(MAP_FIXED)` 在**堆区域内**创建 guard page：

```
时序：
1. sys_sbrk 扩展堆到 0x120200000，权限 R|W|U
2. LoongArch musl malloc 调用:
   mmap(0x1201fe000, 0x1000, PROT_NONE, MAP_FIXED|MAP_PRIVATE|...) 
   → 在堆起始处创建不可读写的 guard page
3. unmap_range 删除/缩小原堆区域
4. insert_mmap_area 创建新区域，权限只有 U（无 R|W）
5. 下次 sys_sbrk 调用 append_to 查找 heap_bottom 地址的区域
6. 找到的是 mmap 创建的 PROT_NONE 区域！
7. 新映射的堆页面没有写权限 → SIGSEGV
```

### 5.2 为什么这属于"特殊情况"而非"正常冲突"

正常情况下，musl/glibc 的 `mmap(NULL, ...)` 由内核选择地址，不会与堆重叠。

但 LoongArch musl 使用 `MAP_FIXED` **强制**在指定地址（恰好在 heap_bottom 附近）映射 guard page，这是一种**故意的重叠**，用于检测堆溢出。

这种行为暴露了内核实现的假设问题：
- 内核假设 heap_bottom 处的 VMA 一定是堆区域
- 但 `mmap(MAP_FIXED)` 可以覆盖任何地址

### 5.3 修复策略

rcore-lab 通过权限验证识别真正的堆区域：

```rust
pub fn append_to_heap(&mut self, heap_bottom: VirtAddr, new_end: VirtAddr) -> bool {
    let expected_perm = MapPermission::R | MapPermission::W | MapPermission::U;
    
    // 只有 R|W|U 权限的区域才是真正的堆
    if let Some(area) = self.areas.iter_mut().find(|a| 
        a.vpn_range.get_start() == heap_bottom.floor() && 
        a.map_perm == expected_perm
    ) {
        area.append_to(&mut self.page_table, new_end.ceil());
        return true;
    }
    
    // 未找到有效堆 → 创建新区域
    let map_area = MapArea::new(heap_bottom, new_end, MapType::Framed, expected_perm);
    self.push(map_area, None);
    true
}
```

## 六、总结

### 6.1 关键数值汇总

| 常量 | rcore-lab | rustoswhu | chronix (RV64) |
|------|-----------|-----------|----------------|
| USER_MMAP_TOP | 0x6_0000_0000 (24GB) | 0x11_0000_0000 (68GB) | ~0x3F_FF00_0000 (240GB) |
| heap_bottom | 动态，~0x4010_0000 (PIE) | 动态 | 动态，紧随 ELF |
| vload_base (PIE) | 0x4000_0000 (1GB) | 未明确 | ELF 原地址 |
| DL_INTERP_OFFSET | 紧随主 ELF | 0x15_0000_0000 (84GB) | 0x20_0000_0000 (128GB) |
| USER_STACK_TOP | 0x8_0000_0000 (32GB) | 0x13_0000_0000 (76GB) | 0x3F_FFFF_F000 (~256GB) |

### 6.2 Linux 规范符合度排名

1. **chronix** - 最符合 Linux 布局规范（mmap 在栈下方，向低地址分配）
2. **rcore-lab** - 功能完备但布局非标准（mmap 与栈分离，向高地址分配）
3. **rustoswhu** - 配置分散，实际行为需进一步验证

### 6.3 mmap 冲突避免机制

1. **内核选址**：`mmap(NULL, ...)` 由内核在空闲区域分配，自动避免冲突
2. **区域类型保护**：`MapAreaType::Heap/Stack/ElfSegment` 阻止 `munmap` 破坏关键区域
3. **地址布局隔离**：关键区域之间保留大量空隙

### 6.4 LA musl 堆损坏的教训

musl 的架构差异行为（`mmap(MAP_FIXED)` 在堆区）暴露了内核对"堆区域识别"的假设缺陷。修复方案：使用**权限验证**而非**地址匹配**来识别堆区域。

## 七、按需分页与物理页节省机制对比

### 7.1 特性支持总览

| 特性 | rcore-lab | rustoswhu | chronix |
|------|-----------|-----------|---------|
| **COW fork** | ✅ 完整 | ✅ 完整 | ✅ 完整 |
| **栈/堆懒分配** | ❌ 预分配 | ✅ Lazy | ✅ Lazy |
| **mmap 懒分配** | ❌ 预分配 | ✅ Lazy | ✅ Lazy |
| **文件映射按需加载** | ❌ | ✅ | ✅ |
| **共享内存** | ✅ SysV SHM | ✅ | ✅ |

### 7.2 COW (Copy-on-Write) fork 实现对比

三个内核都实现了 COW fork，但实现细节有差异：

#### rcore-lab (`os/src/mm/memory_set.rs:818-903`)

```rust
pub fn from_existed_user(parent_space: &mut Self) -> Self {
    // 1. 遍历父进程所有 MapArea
    for area in parent_space.areas.iter_mut() {
        // 2. 共享物理页帧 (clone Arc<FrameTracker>)
        let shared_frame = frame_arc.clone();
        
        // 3. 可写页标记为只读（父子都是）
        if is_writable && src_flags.contains(PTEFlags::W) {
            let ro_flags = src_flags & !PTEFlags::W;
            parent_space.page_table.change_pte_flags(vpn, ro_flags);
        }
        
        // 4. 子进程映射为只读
        child.page_table.map(vpn, shared_frame.ppn, child_flags);
    }
}

pub fn handle_cow_fault(&mut self, addr: usize) -> bool {
    // 5. 写入时触发 page fault
    // 6. 检查 Arc::strong_count
    if Arc::strong_count(frame_arc) == 1 {
        // 唯一持有者：直接恢复写权限
        self.page_table.change_pte_flags(fault_vpn, new_flags);
    } else {
        // 多个持有者：分配新页，复制数据
        let new_frame = frame_alloc();
        new_ppn.get_bytes_array().copy_from_slice(old_ppn.get_bytes_array());
        area.data_frames.insert(fault_vpn, Arc::new(new_frame));
    }
}
```

**特点**：使用 `Arc::strong_count()` 判断是否需要真正复制，避免不必要的拷贝。

#### rustoswhu (`os/src/mm/memory_set.rs:215-246`)

```rust
pub fn handle_cow_addr(&mut self, addr: usize) -> SysResult<isize> {
    if mp.contains(MappingFlags::cow) {
        // 使用专用 COW 标志位
        if Arc::strong_count(frame) == 1 {
            mp |= MappingFlags::W;
            mp &= !MappingFlags::cow;  // 清除 COW 标志
        } else {
            // 分配新页，复制数据
            area.unmap_one(&self.page_table, vpn);
            area.map_one(&self.page_table, vpn);
            dst_ppn.get_buffer().copy_from_slice(src_ppn.get_buffer());
        }
    }
}
```

**特点**：使用专用 `MappingFlags::cow` 标志位标记 COW 页面，而非仅依赖权限位。

#### chronix (`os/src/mm/vm/uvm.rs:751-805`)

```rust
pub fn handle_page_fault(&mut self, page_table: &mut PageTable, vpn: VirtPageNum, 
                          access_type: PageFaultAccessType) -> Result<(), ()> {
    // PTE 有效但只读，且是写访问
    if pte.is_valid() && !pte.is_writable() && access_type.contains(WRITE) {
        if self.map_flags.contains(MapFlags::SHARED) {
            // 共享映射：直接恢复写权限
            pte.set_writable(true);
        } else if old_frame.get_owners() > 1 {
            // COW：分配新页，复制数据
            let new_frame = frames_alloc(1).unwrap();
            new_frame.copy_from(old_frame);
            pte.set_ppn(new_frame.range_ppn.start);
            old_frame.emplace(new_frame);  // 原地替换
        }
        pte.set_writable(true);
    }
}
```

**特点**：使用 `get_owners()` 方法（类似引用计数），统一处理 COW 和共享映射。

### 7.3 栈/堆/mmap 懒分配（Lazy Allocation）

#### rcore-lab: **无懒分配**

rcore-lab 在 `sys_sbrk`、`sys_mmap`、用户栈创建时**立即分配并映射物理页**：

```rust
// os/src/mm/memory_set.rs - MapArea::map() 立即分配所有页
pub fn map(&mut self, page_table: &mut PageTable) {
    for vpn in self.vpn_range {
        self.map_one(page_table, vpn);  // 立即分配 frame
    }
}
```

**代码证据**（`os/src/syscall/process.rs:1096`）：
```rust
// TODO: Replace eager read_all() in exec with a file-backed Reader + lazy page loading.
```

这个 TODO 说明 rcore-lab 目前是"急切"（eager）分配，而非懒分配。

#### rustoswhu: **完整懒分配**

rustoswhu 在 trap handler 中处理懒分配（`os/src/main.rs:149-158`）：

```rust
StorePageFault(_paddr) | LoadPageFault(_paddr) | InstructionPageFault(_paddr) => {
    // 1. 先尝试懒分配
    if memory_set.handle_lazy_addr(_paddr, trap_type).is_err() {
        // 2. 不是懒分配，尝试 COW
        if memory_set.handle_cow_addr(_paddr).is_err() {
            // 3. 都失败，SIGSEGV
        }
    }
}
```

懒分配实现（`os/src/mm/memory_set.rs:150-213`）：
```rust
pub fn handle_lazy_addr(&mut self, addr: usize, _type: TrapType) -> SysResult<isize> {
    // 检查地址是否在 Heap/Stack/Mmap 区域
    for area in self.areas.iter_mut() {
        if (area.area_type == MapAreaType::Heap || 
            area.area_type == MapAreaType::Stack) {
            // 分配单页并映射
            area.map_one(&self.page_table, VirtPage::new(addr / PAGE_SIZE));
            return Ok(0);
        }
    }
    // Mmap 区域：还需要从文件读取数据
    if area.map_file.is_some() {
        file.read_at(off, &mut buf)?;
        dst_ppn.get_buffer().copy_from_slice(&buf);
    }
}
```

#### chronix: **完整懒分配 + 类型化处理**

chronix 对不同 VMA 类型使用专门的 handler（`os/src/mm/vm/uvm.rs:792-801`）：

```rust
// PTE 无效，触发懒分配
_ => {
    match self.vma_type {
        UserVmAreaType::Data =>
            UserDataHandler::handle_lazy_page_fault(self, page_table, vpn, access_type),
        UserVmAreaType::Stack =>
            UserStackHandler::handle_lazy_page_fault(self, page_table, vpn, access_type),
        UserVmAreaType::Heap =>
            UserHeapHandler::handle_lazy_page_fault(self, page_table, vpn, access_type),
        UserVmAreaType::Mmap =>
            UserMmapHandler::handle_lazy_page_fault(self, page_table, vpn, access_type)
    }
}
```

### 7.4 物理页节省效果评估

| 场景 | rcore-lab | rustoswhu | chronix |
|------|-----------|-----------|---------|
| `fork()` 后未写入 | ✅ 共享页 | ✅ 共享页 | ✅ 共享页 |
| `brk(+10MB)` 但只用 1 页 | ❌ 分配 2560 页 | ✅ 分配 1 页 | ✅ 分配 1 页 |
| `mmap(100MB)` 但只访问 4KB | ❌ 分配 25600 页 | ✅ 分配 1 页 | ✅ 分配 1 页 |
| 8MB 用户栈只用栈顶 4KB | ❌ 分配 2048 页 | ✅ 分配 1 页 | ✅ 分配 1 页 |

**典型场景物理内存占用对比**（假设 fork 后子进程只执行 `exec`）：

| 内核 | 父进程 100 页可写 | fork 后共享 | 子进程 exec 前写 1 页 |
|------|------------------|-------------|---------------------|
| rcore-lab | 100 | 100 (共享) | 101 (+1 COW) |
| rustoswhu | 100 | 100 (共享) | 101 (+1 COW) |
| chronix | 100 | 100 (共享) | 101 (+1 COW) |

三者在 COW 场景下效果相同。**差异主要在懒分配**：

假设进程申请 `brk(+100MB)` 但只访问首尾各 1 页：

| 内核 | 物理页分配 |
|------|-----------|
| rcore-lab | 25600 页 (100MB 全分配) |
| rustoswhu | 2 页 (按需) |
| chronix | 2 页 (按需) |

### 7.5 实现复杂度对比

| 方面 | rcore-lab | rustoswhu | chronix |
|------|-----------|-----------|---------|
| page fault 处理 | 仅 COW | COW + Lazy | COW + Lazy (分类型) |
| VMA 状态追踪 | 简单 | 中等 | 复杂 (多种 Handler) |
| 调试难度 | 低 | 中 | 高 |
| 性能 (首次访问) | 快 (已映射) | 慢 (需 fault) | 慢 (需 fault) |
| 内存效率 | 低 | 高 | 高 |

### 7.6 结论

1. **rustoswhu 和 chronix 都实现了完整的按需分页**（COW + 懒分配），能有效减少物理页消耗。

2. **rcore-lab 仅实现 COW**，栈/堆/mmap 使用"急切分配"，物理内存利用效率较低。

3. **chronix 的设计最为模块化**，使用类型化的 VMA Handler 处理不同区域的懒分配，易于扩展但复杂度高。

4. **rustoswhu 的实现最为直接**，在统一的 `handle_lazy_addr` 中处理所有懒分配场景。

5. **对于内存受限场景（如嵌入式/竞赛）**，rustoswhu 和 chronix 的懒分配策略更优；对于追求简单稳定，rcore-lab 的急切分配更易调试。
