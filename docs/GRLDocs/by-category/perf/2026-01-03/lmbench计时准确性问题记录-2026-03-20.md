# lmbench 计时准确性问题记录（待团队接手）

日期：2026-03-20  
分支：`glibc-test / lmbench-test`（以本地实际分支为准）

## 1. 背景

glibc lmbench 套件已可运行，`unimplemented syscall` 与 `sepc=0x4000` 级别故障已清理。
当前剩余问题是：lmbench 指标数值偏慢且可信度不足，需要团队后续专门做计时语义与性能口径收敛。

## 2. 观测到的现象

- lmbench 已进入执行并输出结果（如 `Simple syscall/read/write/stat`）。
- 同时日志显示 lmbench 高频调用：
  - `clock_gettime`（syscall 113）
  - `getrusage`（syscall 165）
- 时间源与频率存在潜在不一致风险：
  - OpenSBI 报告平台定时器 `aclint-mtimer @ 10000000Hz`
  - 内核常量 `CLOCK_FREQ = 12_500_000`

## 3. 当前实现状态（代码事实）

1. 时间读取路径
- `arch/src/riscv64/timer.rs` 使用 `time::read()` 并按 `CLOCK_FREQ` 换算。
- `get_time_us()`：`time::read() * 1_000_000 / CLOCK_FREQ`。

2. clock_gettime 语义
- `os/src/syscall/process.rs::sys_clock_gettime()` 实际用 `get_time_us()` 再乘 1000 得到 `tv_nsec`。
- 本质是“微秒级时间戳扩展为纳秒字段”，不是纳秒精度时间源。

3. getrusage 语义
- `os/src/syscall/process.rs::sys_getrusage()` 当前返回的是基于 `get_time_us()` 的近似值。
- `ru_utime`/`ru_stime` 不是严格的 per-process/per-thread CPU accounting。

## 4. 风险评估

1. 频率不一致风险
- 若 `CLOCK_FREQ` 与硬件/仿真 `mtime` 频率不一致，会造成系统性时间缩放误差。

2. 计时精度风险
- lmbench 对微秒级差异敏感。
- 目前 clock_gettime/getrusage 语义偏“可用”而非“benchmark 级准确”。

3. 指标解释风险
- 当前分数可用于回归对比（同内核版本内），不宜直接与官方标杆做强对齐。

## 5. 建议由团队后续处理的任务

1. 校准时间基准
- 统一 `CLOCK_FREQ` 与 QEMU/OpenSBI 报告频率。
- 验证 `mtime` 到 us/ns 的换算误差。

2. 提升 clock_gettime 口径
- 评估是否提供更细粒度或更稳定的 ns 级转换策略。
- 明确 `CLOCK_REALTIME` 与 `CLOCK_MONOTONIC` 的语义边界。

3. 补齐 getrusage 统计语义
- 至少区分 `RUSAGE_SELF / THREAD / CHILDREN` 的统计来源。
- 建立基础 CPU 时间记账（user/system）框架。

4. 复核 lmbench 测量链路
- 抽离“日志开销”影响（仅 `LOG=OFF` 下对比）。
- 增加一次固定场景 A/B 对照（修复前后 + 官方参考口径）。

## 6. 交接结论

- 本轮工作已完成“可运行与兼容性修复”目标。
- “计时精度与性能口径”问题已定位到时间源与语义层，建议转团队专项处理。
