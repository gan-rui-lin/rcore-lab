# rcore-lab 架构细节屏蔽机制与解耦改进（2026-05-25）

## 一、本文与 ZJYDocs 多架构移植系列的关系

`docs/ZJYDocs/多架构移植/` 下已经有一组按机制拆分的多架构文档，例如：

- `Trap处理抽象.md`：重点解释 trap 上下文、异常分类、汇编入口和 `TrapFrameArgs` 这类寄存器抽象。
- `页表抽象.md`：重点解释地址类型、PTE 编码、页表遍历、TLB 刷新和 MMU 切换。
- `定时器与中断抽象.md`：重点解释不同架构的定时器、中断控制器和外部中断处理。
- `上下文切换抽象.md`：重点解释内核上下文、callee-saved 寄存器、TLS 和页表切换。
- `启动流程抽象.md`、`LoongArch启动流程深度分析.md`：重点解释启动模型、DMW、初始页表和链接脚本差异。

本文不重复展开寄存器位、PTE 位、LoongArch TLB refill、RISC-V `satp` 等细节，而是横向回答三个问题：

1. rcore-lab 当前到底靠哪些机制屏蔽架构细节；
2. 这些架构细节主要有哪些类型，哪些已经隔离，哪些仍泄漏到 OS 层；
3. 围绕设备、中断、trap、页表，后续怎样设计才能提高解耦能力。

一句话概括当前状态：rcore-lab 已经把最核心的 CPU、Trap、页表实现迁到了 `arch` crate，但 `os` crate 中仍存在若干平台策略、设备模型和内存布局差异，尤其集中在 `board`、`drivers`、`trap` 和 `memory_set`。

## 二、rcore-lab 当前如何屏蔽架构细节

### 1. `arch` crate 作为 CPU 与 MMU 差异承载层

当前 `arch/src/lib.rs` 通过 `cfg_attr(target_arch = "...", path = "...")` 选择具体架构模块：

```rust
#[cfg_attr(target_arch = "riscv64", path = "riscv64/mod.rs")]
#[cfg_attr(target_arch = "loongarch64", path = "loongarch64/mod.rs")]
mod current_arch;

pub use current_arch::*;
```

这是一种健康的边界：`target_arch` 出现在 arch crate 的入口分发处，属于架构选择本身，而不是业务策略分支。每个架构模块再 re-export 同一批符号，例如：

- `PageTable`、`PageTableEntry`、`PTEFlags`
- `PhysAddr`、`VirtAddr`、`PhysPageNum`、`VirtPageNum`
- `TrapContext`、`TaskContext`
- `enter_user_and_trap`
- `trap_init`、`trap_enable_timer_interrupt`
- `get_time_ms`、`set_next_trigger`
- `console_putchar`、`shutdown`

因此 `os` crate 可以尽量只写 `arch::*`，不直接知道底层是 RISC-V 还是 LoongArch。

### 2. 统一枚举屏蔽寄存器和异常码

`arch/src/lib.rs` 中定义了两个关键枚举：

- `TrapFrameArgs`：把 `SEPC`、`RA`、`SP`、`RET`、`ARG0`、`TLS`、`SYSCALL` 等概念抽象出来。
- `TrapType`：把硬件异常与中断统一分类为 `UserEnvCall`、`Time`、`SupervisorExternal`、`LoadPageFault`、`StorePageFault`、`IllegalInstruction` 等。

不同架构的 `TrapContext` 可以有完全不同的寄存器布局，但只要实现 `Index<TrapFrameArgs>` / `IndexMut<TrapFrameArgs>`，OS 层就能用同一套方式读写 syscall 参数、返回值、线程指针和异常 PC。

异常分类也类似。RISC-V 读取 `scause/stval`，LoongArch 读取 `estat/badv`，但上交给 OS 的都是 `TrapType`。这样 `os/src/trap/mod.rs` 的主循环可以围绕“这是系统调用、时钟中断、页故障还是非法指令”写内核策略，而不是关心硬件编码。

### 3. `ArchInterface` 反向回调避免 crate 循环依赖

`arch/src/api.rs` 定义了 `ArchInterface`，由 `os/src/main.rs` 实现。这个接口解决的是反向依赖问题：arch crate 需要分配页表页、释放页表页、获取 kernel page table token、把内核态中断交还给 OS，但不能直接依赖 `os::mm` 或 `os::trap`。

当前关键回调包括：

- `frame_alloc()` / `frame_dealloc(ppn)`
- `kernel_page_table_token()`
- `kernel_interrupt(trap_type)`

页表实现通过这些回调拿到物理页，trap 实现通过 `kernel_interrupt()` 把内核态 timer/external interrupt 交给 `os/src/trap/mod.rs` 的 `kernel_interrupt_dispatch()`。

这个设计的价值是：页表分配、Trap 分类、硬件入口仍在 arch 层，但资源所有权和内核策略留在 OS 层。

### 4. `os::mm` 通过 re-export 使用架构页表

`os/src/mm/mod.rs` 当前直接 re-export arch 页表相关类型：

```rust
pub use arch::{
    translated_byte_buffer, translated_byte_buffer_checked, translated_ref, translated_refmut,
    translated_str, translated_str_checked, PTEFlags,
};
pub use arch::{PageTable, PageTableEntry, UserBuffer, UserBufferIterator};
pub use arch::{PhysAddr, PhysPageNum, StepByOne, VPNRange, VirtAddr, VirtPageNum};
```

这说明页表的核心实现已经从 OS 层下沉到 arch 层。`MemorySet`、`MapArea`、用户内存访问、COW 和 demand paging 等上层逻辑仍然在 `os::mm`，但它们面向的是统一的 `PageTable` API。

### 5. board 与 driver 层承担设备差异

设备侧目前不是完全放入 `arch` crate，而是由 `os/src/main.rs` 选择 board 模块：

```rust
#[cfg_attr(target_arch = "riscv64", path = "boards/qemu.rs")]
#[cfg_attr(target_arch = "loongarch64", path = "boards/qemu_la.rs")]
mod board;
```

RISC-V board 绑定 `VirtIOBlock`、NS16550a UART、PLIC、input 和 net IRQ；LoongArch board 绑定 `VirtIOPCIBlock`，并把外部中断 dispatch 暂时做成 stub。块设备再通过 `BlockDeviceImpl` 和 `Arc<dyn BlockDevice>` 进入文件系统层，所以 FAT32/ext4/easy-fs 基本不关心底层是 MMIO virtio-blk 还是 PCI virtio-blk。

这是一种“部分屏蔽”：块设备到文件系统的边界较干净，但设备发现、IRQ 编号、claim/complete、网卡与 UART 等还没有统一平台抽象。

## 三、架构细节主要有哪些

rcore-lab 中需要屏蔽的架构细节大致可以分为六类。

### 1. 启动、特权级与控制寄存器

这类包括入口汇编、初始栈、BSS 清零、特权级切换、异常向量设置、页表启用顺序和链接脚本。

RISC-V 的启动路径偏向“先建立页表，再切高半地址空间”；LoongArch 使用 DMW 后，早期访问模型和 TLB refill 机制完全不同。这类差异很难强行统一，适合留在 `arch::{entry, trap, board}` 这类边界模块里。

### 2. Trap 上下文与 ABI

这类包括通用寄存器布局、syscall 参数寄存器、返回值寄存器、TLS 寄存器、异常 PC、异常返回指令和信号上下文布局。

当前屏蔽方式主要是：

- `TrapContext` 每架构自定义；
- `TrapFrameArgs` 提供统一索引；
- `MContext`、`FpRegs` 等信号相关类型由 arch re-export；
- OS 层尽量通过 `trap_cx[TrapFrameArgs::...]` 访问关键寄存器。

### 3. 页表、MMU 与 TLB

这类包括虚拟地址宽度、物理地址宽度、页表层级、PTE 编码、权限语义、页表 token、TLB 刷新和内核高半映射。

当前 `PageTable` 已经在 arch 层分架构实现，但 `MemorySet` 中仍能看到架构泄漏，例如：

- RISC-V 高半线性映射安装逻辑；
- LoongArch 的信号跳板映射位置；
- `flush_tlb()` / `flush_tlb_page()` 中直接写 `sfence.vma` 或 `invtlb`；
- 部分 LoongArch 调试日志和地址限制判断散落在通用内存管理逻辑中。

### 4. 定时器与中断控制器

定时器细节包括计数器频率、一次性 timer 与周期 timer、清中断方式、下次触发设置方式。RISC-V 通过 SBI/mtime 设置下一次 timer，LoongArch timer 更偏周期配置。

中断控制器细节包括 PLIC、EIOINTC、CPU 本地中断线、IRQ 编号、claim/complete、优先级和阈值。当前 timer 已经通过 `arch::{get_time_ms, set_next_trigger}` 屏蔽得比较好，但外部中断还主要由 board 函数直接分发。

### 5. 设备、MMIO 与 DMA

设备差异包括：

- 设备发现方式：硬编码 MMIO、PCI 枚举、设备树或固件表；
- MMIO 地址空间：RISC-V QEMU virt 的 UART/PLIC/VirtIO MMIO，LoongArch 的 PCI ECAM 与 DMW；
- DMA 地址转换：RISC-V virtio HAL 用 kernel page table 翻译虚拟地址，LoongArch virtio HAL 使用 DMW 直接映射窗口；
- 中断模式：轮询、PLIC 外部中断、PCI/MSI 或平台中断控制器。

当前块设备屏蔽较好，网络、输入、串口和外部中断屏蔽还不完整。

### 6. 用户态 ABI 与兼容路径

这类包括 syscall 编号、`uname.machine`、动态链接器路径、信号 trampoline 地址、`ucontext` 布局、TLS/AUXV 差异等。

这部分不一定全部属于“硬件架构层”，有些是 Linux ABI 或用户态发行版约定。它们可以通过 arch hook 隔离，但不应该混进页表、trap 或设备驱动内部。

## 四、重点模块现状

### 1. 设备：块设备边界较干净，平台设备模型仍分散

设备层当前最成功的抽象是块设备。

`os/src/boards/qemu.rs` 中：

```rust
pub type BlockDeviceImpl = crate::drivers::block::VirtIOBlock;
```

`os/src/boards/qemu_la.rs` 中：

```rust
pub type BlockDeviceImpl = crate::drivers::block::VirtIOPCIBlock;
```

`os/src/drivers/block/mod.rs` 再用这个别名创建 `Arc<dyn BlockDevice>`，文件系统层只拿 `BLOCK_DEVICE`，不再关心设备来自 MMIO 还是 PCI。这条链路的分层是清晰的：

```text
board 选择具体设备
  -> drivers/block 包装为 BlockDevice
  -> fs/vfs/ext4/fat32 只依赖 Arc<dyn BlockDevice>
```

泄漏点主要有三个：

1. `drivers/mod.rs` 中 `chardev`、`input`、`net`、`plic` 仍标注 RISC-V only，说明设备子系统不是面向平台能力统一组织，而是按当前 RISC-V QEMU virt 设备集合展开。
2. RISC-V 的 `board::irq_handler()` 直接 claim PLIC 并 match IRQ 编号，然后调用 UART、block、net、keyboard、mouse handler；这把中断控制器、IRQ 表和设备对象绑在一个函数里。
3. LoongArch 的 `board::irq_handler()` 目前只记录 warning，实际块设备依赖 polling 路径，外部 IRQ dispatch 还没有成型。

因此设备层的现状可以概括为：块设备到文件系统的抽象已经可用，但“平台总线 + IRQ 路由 + 设备注册表”还没有形成统一模型。

### 2. 中断：TrapType 屏蔽了 CPU 中断分类，但没有屏蔽 IRQ 控制器

时钟中断的屏蔽相对成熟。`os/src/timer.rs` 只 re-export：

```rust
pub use arch::{get_time, get_time_ms, get_time_us, set_next_trigger};
```

RISC-V 和 LoongArch 可以分别实现一次性触发或周期触发，OS 层统一调用 `set_next_trigger()`、`check_timer()`、`process_interval_timers()`。

外部中断则只完成了第一层屏蔽。arch 层把硬件中断分类成 `TrapType::SupervisorExternal`，OS 层在 `kernel_interrupt_dispatch()` 中调用 `crate::board::irq_handler()`。但进入 board 之后，仍然是平台专用逻辑：

- RISC-V：PLIC `claim()`、match IRQ、调用设备 handler、`complete()`。
- LoongArch：暂未实现完整 routing。

也就是说，当前抽象只屏蔽了“这是一个外部中断”，没有屏蔽“如何从中断控制器拿到 IRQ、如何确认完成、IRQ 和设备如何绑定”。

更好的边界应该是：

```text
arch trap classifier
  -> TrapType::SupervisorExternal
  -> IrqController::claim()
  -> BoardDevices::dispatch(irq)
  -> IrqController::complete(irq)
```

这样 PLIC、LoongArch 中断控制器、PCI IRQ/MSI 都可以放在 `IrqController` 实现里，board 只负责提供设备表。

### 3. Trap：硬件分类已统一，用户态策略仍有架构泄漏

Trap 主路径已经比早期干净很多。`os/src/trap/mod.rs` 的 `user_trap_loop()` 大体是统一的：

```text
enter_user_and_trap()
  -> match TrapType
  -> syscall / timer / external / page fault / illegal / breakpoint
  -> handle_signals()
```

硬件相关部分已经下沉到 arch：

- RISC-V 的 `scause/stval/stvec/sscratch` 处理在 `arch/src/riscv64/trap`；
- LoongArch 的 `estat/badv/eentry/tlbrentry` 处理在 `arch/src/loongarch64/trap.rs`；
- 两边最终都返回 `TrapType`。

OS 层仍保留：

```rust
#[cfg_attr(target_arch = "riscv64", path = "user_trap_riscv64.rs")]
#[cfg_attr(target_arch = "loongarch64", path = "user_trap_loongarch64.rs")]
mod user_trap_arch;
```

这说明策略层仍有差异。比如 RISC-V breakpoint 需要根据压缩指令长度推进 `sepc`，LoongArch 的非法指令日志和 sigreturn 诊断不同，外部中断处理也不同。

这种分叉目前是可接受的，因为它已经从“复制整套 trap 主循环”收敛为“统一主循环 + 架构 helper”。下一步可以继续把 helper 再拆成更小的 arch hook，例如：

- `arch::trap::breakpoint_advance_pc(trap_cx)`
- `arch::trap::format_fault_context(trap_cx, addr)`
- `arch::trap::is_sigreturn_trampoline_pc(pc)`

OS 层只保留信号投递、COW/demand fault、syscall 分发等内核策略。

### 4. 页表：核心实现已下沉，地址空间策略仍混在 MemorySet

页表的核心实现已经从 OS 层迁移到 arch 层。RISC-V 和 LoongArch 各自提供 `PageTable`、`PageTableEntry`、`PTEFlags`、地址类型、用户内存翻译函数。`os::mm` 上层统一使用这些类型。

当前优势：

- `PageTable::new()`、`map()`、`unmap()`、`translate()`、`token()` 都由 arch 实现；
- PTE 编码差异不再暴露给大部分 OS 代码；
- 页表节点分配通过 `ArchInterface` 回调 OS frame allocator，避免 crate 循环依赖；
- `translated_*_checked` 一类用户内存访问路径可以按架构处理 PTE 权限语义。

主要问题在 `os/src/mm/memory_set.rs`。这里承载了太多“地址空间策略”和“架构细节”的混合逻辑：

- `flush_tlb()` 直接根据架构写 `sfence.vma` 或 `invtlb`；
- RISC-V 需要安装高半线性 root 映射；
- LoongArch 用户信号跳板映射位置与权限特殊；
- MMIO、内核段、物理内存映射策略对不同架构不是同一个模型；
- 个别 LoongArch 调试与保护判断混在通用 `MapArea` 流程中。

这里的本质问题是：`PageTable` 是硬件页表抽象，`MemorySet` 是 OS 地址空间策略；但现在一些“架构地址空间策略”没有单独抽象，只能散落在 `MemorySet` 的 `target_arch` 分支里。

更好的做法不是把所有逻辑硬塞进 `PageTable`，而是新增一层 `ArchMemoryOps` 或 `AddressSpacePolicy`：

```rust
trait ArchMemoryOps {
    fn flush_tlb_all();
    fn flush_tlb_page(va: usize);
    fn install_kernel_mappings(page_table: &mut PageTable);
    fn map_user_trampoline(memory_set: &mut MemorySet, stack_bottom: usize);
    fn validate_user_ppn(ppn: PhysPageNum, flags: PTEFlags) -> bool;
}
```

这样 `PageTable` 仍负责页表结构，`MemorySet` 仍负责 VMA 与映射生命周期，架构相关地址空间策略则集中到可审查的 hook 中。

## 五、解耦能力评价与改进设计

### 1. 当前设计的优点

当前 rcore-lab 的架构解耦已经具备几个关键基础：

1. `arch` crate 成为明确边界，避免 OS 大量直接使用 `riscv` 或 `loongArch64` crate。
2. `TrapType` 和 `TrapFrameArgs` 把 trap 分类和寄存器 ABI 做了统一抽象。
3. 页表实现已经进入 arch 层，上层 `MemorySet` 不再直接操作某一种硬件 PTE 格式。
4. `ArchInterface` 解决了 arch 层需要 OS 资源时的反向调用问题。
5. 块设备已经通过 trait object 屏蔽到文件系统层，证明这条分层路线可行。

这些改造已经把“最硬”的 CPU/MMU 差异隔离了一大块。后续工作的重点不是推倒重来，而是把残留的 `target_arch` 从 OS 策略层继续挤压到边界层。

### 2. 当前设计的主要短板

主要短板可以归纳为四个：

1. **board 层职责过重**：同时负责设备选择、PLIC 初始化、IRQ 表、设备 handler 分发。它既是平台描述，又是中断控制器驱动，又是设备管理器。
2. **中断控制器没有 trait 化**：`SupervisorExternal` 只说明“有外部中断”，但 claim/complete 和 IRQ routing 仍是硬编码。
3. **MemorySet 里混入架构策略**：TLB flush、内核映射、跳板映射、地址空间布局策略还没有从通用 VMA 逻辑中分离。
4. **用户态 ABI hook 分散**：信号跳板、动态链接器路径、`uname.machine`、ucontext 等差异散布在 task/fs/syscall/mm 多处。

### 3. 建议的演进路线

#### Phase 1：先把显性硬件操作收敛成 arch hook

优先处理低侵入、高收益的点：

- `flush_tlb()` / `flush_tlb_page()` 迁移为 `arch::flush_tlb_all()` / `arch::flush_tlb_page(va)`；
- breakpoint PC 推进、sigreturn trampoline 判断、fault context dump 迁移为 `arch::trap` helper；
- `uname.machine`、动态链接器默认路径、信号 trampoline 地址集中到 `arch::abi` 或 `arch::user_abi`。

目标不是减少代码行数，而是让 OS 层看不到具体指令和架构名称。

#### Phase 2：拆出 `IrqController` 与 `BoardDevices`

建议把外部中断拆成两个接口：

```rust
trait IrqController {
    fn init(&self);
    fn claim(&self) -> Option<u32>;
    fn complete(&self, irq: u32);
}

trait BoardDevices {
    fn init_devices(&self);
    fn dispatch_irq(&self, irq: u32);
}
```

RISC-V QEMU virt 可以实现为 PLIC + MMIO VirtIO/UART/input/net；LoongArch QEMU virt 可以实现为 PCI VirtIO + 后续的 LoongArch IRQ controller。这样 `kernel_interrupt_dispatch()` 不需要知道 PLIC，也不需要知道 IRQ 号和设备对象如何匹配。

#### Phase 3：引入 `PlatformConfig`

当前 MMIO 地址、IRQ 号、RAM 结束地址、DMA 转换方式分散在 board、driver、arch board consts 中。可以逐步引入静态平台描述：

```rust
struct PlatformConfig {
    memory_end: usize,
    mmio_regions: &'static [(usize, usize)],
    devices: &'static [DeviceDesc],
    dma_mode: DmaMode,
}

struct DeviceDesc {
    kind: DeviceKind,
    transport: DeviceTransport,
    irq: Option<u32>,
}
```

第一阶段不必支持完整设备树，只需要把现有 QEMU virt 的硬编码收纳成结构化数据。这样后续迁移到 FDT、ACPI 或 LoongArch 固件表时，OS 上层接口可以保持稳定。

#### Phase 4：拆出 `ArchMemoryOps` / `AddressSpacePolicy`

`MemorySet` 是当前架构泄漏最多的地方，不建议一次性大重构。比较稳的路线是：

1. 先抽 TLB flush；
2. 再抽内核映射安装策略；
3. 再抽用户 trampoline 映射策略；
4. 最后收敛地址合法性检查和 debug dump。

最终目标是让 `MemorySet` 只表达 OS 语义：

- 这个 VMA 是匿名页、文件页、栈、堆还是 mmap；
- 权限是 R/W/X/U 的哪几种；
- 是否 lazy、是否 COW、是否 MAP_SHARED；
- fault 时如何补页或发信号。

至于“这套语义落到某个架构时要怎么刷 TLB、怎么安装内核映射、跳板页放哪里”，应该交给 arch memory policy。

#### Phase 5：标记或清理历史页表实现

仓库中仍能看到 `os/src/mm/page_table.rs`、`os/src/mm/address.rs` 这类早期 RISC-V 风格实现文件，而当前 `os/src/mm/mod.rs` 已经 re-export `arch` 的页表与地址类型。这类文件容易让读者误判“当前页表实现到底在哪里”。

建议后续做一次清理：

- 如果确认未使用，删除或移动到历史参考目录；
- 如果暂时保留，在文件头注明“legacy / not exported by current mm module”；
- 文档中统一说明当前权威实现以 `arch/src/{riscv64,loongarch64}` 下的页表实现为准。

## 六、结论

rcore-lab 当前的架构细节屏蔽已经从“到处 `target_arch`”进入了“有明确 arch crate 边界，但 OS 层仍有若干残留策略分支”的阶段。

对设备、中断、trap、页表四块可以分别下结论：

- 设备：块设备抽象已经比较干净，但平台设备模型、IRQ 表和外部中断分发仍需统一。
- 中断：CPU trap 分类已经统一为 `TrapType`，但中断控制器和 IRQ routing 还没有 trait 化。
- Trap：硬件入口、异常码、寄存器布局已基本下沉到 arch，OS 主循环已统一，剩余差异应继续缩小为 arch hook。
- 页表：硬件页表实现已迁到 arch，但地址空间策略仍混在 `MemorySet` 中，下一步应抽出 `ArchMemoryOps`。

后续解耦的核心原则不是追求 `target_arch` 绝对清零，而是把它压缩到几个清晰边界：

```text
arch crate       : CPU、MMU、Trap、ABI hook
platform/board   : 设备描述、IRQ 控制器、总线发现
os crate         : 进程、内存语义、文件系统、网络协议栈、信号和 syscall 策略
drivers          : 设备协议实现，通过 trait 暴露给 OS 子系统
```

只要这个边界稳定，后续增加新架构或补齐 LoongArch 设备中断时，需要改动的就主要是 arch/platform/driver 层，而不是把 `target_arch` 继续扩散到 OS 业务路径中。
