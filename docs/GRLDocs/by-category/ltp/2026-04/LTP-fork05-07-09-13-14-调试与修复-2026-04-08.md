# LTP `fork05|fork07|fork09|fork13|fork14` 调试与修复记录（2026-04-08）

## 1. 背景与目标

在 LoongArch 环境下，针对以下 5 个 LTP 用例做回归与修复闭环：

- `fork05`
- `fork07`
- `fork09`
- `fork13`
- `fork14`

目标是：

1. 用最小复现命令快速稳定复现问题；
2. 按测试源码语义定位根因；
3. 修复后给出完整回归结果（含日志证据）。

---

## 2. 复现方法（按单测逐个跑）

统一使用：

```bash
timeout <T> env SINGLE_TEST=/musl/ltp/testcases/bin/<case> LOG=<LEVEL> \
  bash run-la.sh -f sdcard-la.img -t all > /tmp/la-<case>.log 2>&1
```

关键说明：

- `fork13`、`fork14` 本身耗时更长，`timeout` 需要放大（本次使用到 700s）。
- `LOG=INFO` 用于看细节路径；`LOG=WARN` 用于减少日志开销、验证是否“仅日志拖慢”。

## 3. 初始现象

### 3.1 `fork05` / `fork07` / `fork09`

三项基线基本正常：

- `fork05`：`TINFO (%fs test only for ix86)`，`status=0x0`
- `fork07`：`TPASS`，`status=0x0`
- `fork09`：`TPASS`，`status=0x0`

### 3.2 `fork13`

初始失败特征：

- `TFAIL: Unexpected pid sequence: prev_pid=4, pid=4 for iteration=1`
- 后续 `TBROK: Invalid child (4) exit value 1`

这和测试源码 `fork13.c` 的语义一致：它就是在检测“PID 不应立即复用”。

### 3.3 `fork14`

初始是长期循环 + 超时，随后在深入排查阶段出现过 SIGSEGV：

- 早期特征：`clone/wait4/mmap(1GB)` 重复，无法收敛
- 深入阶段特征：`trap_handler: page fault ... name=fork14 ...`，LTP 报 `TBROK: Test killed by SIGSEGV!`

`fork14.c` 的语义是验证大地址空间压力下 fork 的正确失败行为（历史上是 16TB 溢出修复点）。

## 4. 本次是怎么定位出来的（调试路径）

1. **先单测，不跑 all**
   - 逐个只跑目标 case，避免噪声。

2. **先抓结论行，再看细节**
   - 先 `TPASS/TFAIL/TBROK/status`，确认失败类型；
   - 再回看 syscall/异常行找第一偏差点。

3. **对照 LTP 源码语义**
   - `fork13.c`：重点在 PID 序列与 waitpid 回收一致性；
   - `fork14.c`：重点在大 VMA 压力下 fork 失败路径与内存映射稳定性。

4. **区分“慢”与“错”**
   - `fork14` 先把日志降到 `WARN` 排除纯日志开销；
   - 若仍异常，再转向 `mmap/munmap/fork/COW/lazy VMA` 路径。

5. **最终回归按同一模板复验 5 项**
   - 同一命令模板、统一日志提取规则，确保结论可复现。

## 5. 根因归纳（按故障类别）

### 5.1 `fork13` 根因类别

- **PID 生命周期/回收语义不符合测试预期**（表现为 PID 过快复用）。
- 该类问题会直接触发 `fork13` 的 `Unexpected pid sequence`。

### 5.2 `fork14` 根因类别

- **大 VMA 压力下的 `fork + mmap/munmap + lazy` 组合路径不稳定**。
- 典型表现：长时间不收敛（看起来像卡住）或映射破坏后触发 SIGSEGV。

### 5.3 与 Linux 历史 16TB 溢出漏洞（7edc8b0ac16c）的对应关系

你说得对：`fork14` 的历史背景确实是 Linux 早期 `dup_mmap()` 在大映射总量下的整型溢出问题（16TB 量级）。

本内核里，这一类问题主要在以下层面被规避：

1. **没有 `unsigned int` 风格的 VMA 总长度累加点**
   - `fork` 复制地址空间走 `MemorySet::from_existed_user()`，按 area/page 逐项处理，没有“32 位总量累加器”。
   - 位置：`os/src/mm/memory_set.rs:907`。

2. **页数计算使用 `usize`，且带饱和减法**
   - `area_pages` 计算使用 `usize` + `saturating_sub`，不会出现 32 位截断回绕。
   - 位置：`os/src/mm/memory_set.rs:921`、`os/src/mm/memory_set.rs:925`。

3. **`mmap` 地址增长使用 `checked_add` 防溢出**
   - 非 `MAP_FIXED` 寻址时，多次对 `start + len` 做 `checked_add`，溢出直接返回 `ENOMEM`。
   - 位置：`os/src/syscall/process.rs:2622`、`os/src/syscall/process.rs:2643`。

4. **当前地址模型下，16TB 场景本身不可达**
   - 地址类型按 Sv39 处理：`VA_WIDTH_SV39 = 39`（虚拟地址窗口远小于 16TB）。
   - 位置：`os/src/mm/address.rs:7`。
   - 用户态布局上，`USER_MMAP_TOP = 0x6_0000_0000`、`USER_STACK_TOP = 0x8_0000_0000`，即当前用户空间工作区间本身就不到 16TB 量级。
   - 位置：`os/src/config.rs:9`、`os/src/config.rs:11`。

结论：  
本内核不是“照搬 Linux 那个补丁点”，而是在实现与地址空间约束上避免了同类 16TB 整型溢出路径；本次 `fork14` 真正修复的主线仍是 `fork` 全量扫描开销、`mmap` 重叠处理、lazy `munmap` 所有权一致性这三块。

## 6. 代码是怎么修复的（关键改动）

本轮不是只调参数，而是改了内核路径，核心有 4 处。

### 6.1 `fork13`：避免 PID 立即复用

文件：`os/src/task/id.rs`  
位置：`PidHandle::drop()`

改动：不再在 `drop` 时把 PID 放回回收池，而是保持 PID 单调递增。  
目的：避免出现 `prev_pid=4, pid=4` 这类“连续复用”序列，符合 `fork13.c` 的检查语义。

对应代码点：

- `os/src/task/id.rs:93`
- `os/src/task/id.rs:95`

### 6.2 `fork14`：COW fork 对“大而稀疏 VMA”不再全量扫描

文件：`os/src/mm/memory_set.rs`  
位置：`MemorySet::from_existed_user()`

改动：

1. 增加 `FULL_VPN_SCAN_LIMIT` 阈值；
2. 小区域沿用原逻辑（按 `vpn_range` 扫描）；
3. 大稀疏区域改为只遍历 `data_frames`（已物化页）。

目的：避免 `fork14` 中大量 `1GB mmap` 造成 fork 时全量 VPN 扫描，显著降低卡死/超时风险。

对应代码点：

- `os/src/mm/memory_set.rs:912`
- `os/src/mm/memory_set.rs:916`
- `os/src/mm/memory_set.rs:995`

### 6.3 `fork14`：`sys_mmap` 非 `MAP_FIXED` 必须避开重叠区

文件：`os/src/syscall/process.rs`  
位置：`sys_mmap()`

改动：

1. 非 `MAP_FIXED` 时，从 `hint/mmap_base` 起步，循环检查 overlap；
2. 发现 overlap 就跳到最大冲突区末尾继续找空洞；
3. 若最终仍 overlap，直接 `ENOMEM`（而不是带重叠插入）。

目的：避免“新 VMA 与已有 VMA 重叠”导致后续 `munmap` 误伤其他区域（尤其栈/代码相关映射）。

对应代码点：

- `os/src/syscall/process.rs:2606`
- `os/src/syscall/process.rs:2620`
- `os/src/syscall/process.rs:2699`

### 6.4 `fork14`：`munmap` 对 lazy 区域只回收“自己拥有”的页

文件：`os/src/mm/memory_set.rs`  
位置：`unmap_range()` 与 `unmap_one()`

改动：

1. `unmap_range` 在 lazy 区域不再对“无 data_frame 的 vpn”盲目 `page_table.unmap()`；
2. `unmap_one` 改为：lazy 区域仅当该页在 `data_frames` 中存在（即确实由该 VMA 物化）才 unmap。

目的：避免高地址 lazy 映射下的 VPN 别名误删（LoongArch 39-bit 场景下会表现为代码页/执行页异常）。

对应代码点：

- `os/src/mm/memory_set.rs:355`
- `os/src/mm/memory_set.rs:385`
- `os/src/mm/memory_set.rs:1798`

### 6.5 每个修复是如何落地的（修改前 -> 修改后 -> 验证）

#### A. `fork13`（PID 复用）

修改前：

- 子进程退出后，`PidHandle::drop()` 会把 PID 立即放回分配器；
- 下一次 `fork` 可能立刻拿到同一个 PID，触发 `Unexpected pid sequence`。

修改后：

- `PidHandle::drop()` 不再调用 PID 回收；
- PID 仅递增分配，不做短周期复用。

为什么有效：

- `fork13.c` 检查的是“短时间内 PID 序列不应回退/复用”；
- 取消即时回收后，序列满足测试语义。

验证方式：

- 单跑 `fork13`，观察日志从 `TFAIL/TBROK` 变为  
  `TPASS: fork13 ... all passed` 且 `run_all_case status=0x0`。

#### B. `fork14`（fork 时全量扫描导致超时）

修改前：

- `from_existed_user()` 对 VMA 按 `vpn_range` 全量遍历；
- 对 `1GB * N` 的大稀疏映射，fork 时成本极高，出现长时间不收敛。

修改后：

- 新增 `FULL_VPN_SCAN_LIMIT`；
- 小区域继续全扫描；
- 大稀疏区域仅遍历 `data_frames`（真实物化页）并做 COW 映射。

为什么有效：

- 复杂度从“与虚拟区间长度相关”降为“与已分配物理页数量相关”；
- 直接打掉 `fork14` 的超时主因。

验证方式：

- 单跑 `fork14`，确认不再无限循环，最终出现  
  `TPASS: fork() failed as expected`。

#### C. `fork14`（`mmap` 重叠插入破坏地址空间）

修改前：

- 非 `MAP_FIXED` 路径下，地址选择可能与已有 VMA 重叠；
- 重叠 VMA 会在后续 `munmap` 造成误伤。

修改后：

- 非 `MAP_FIXED` 改为“找空洞”策略：发现 overlap 就跳到冲突段末尾继续找；
- 找不到合法空洞时返回 `ENOMEM`。

为什么有效：

- 保证新 VMA 与旧 VMA 不重叠，阻断后续误删链路。

验证方式：

- 观察 `fork14` 压测阶段不再出现由映射破坏引发的异常崩溃路径。

#### D. `fork14`（lazy `munmap` 误删非本区页）

修改前：

- lazy 区域 `munmap` 时，未区分“该页是否由本 VMA 物化拥有”；
- 在高地址/别名场景可能触发错误 `unmap`，引发 SIGSEGV。

修改后：

- `unmap_range()/unmap_one()` 改为仅对 `data_frames` 中存在的页执行 `unmap`；
- 未物化页不触碰页表映射。

为什么有效：

- `munmap` 行为与 VMA 所有权一致，避免误删代码页/执行页映射。

验证方式：

- `fork14` 由“可能 SIGSEGV/TBROK”恢复到稳定 `TPASS`。
