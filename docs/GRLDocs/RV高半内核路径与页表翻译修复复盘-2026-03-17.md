# RV高半内核路径与页表翻译修复复盘

日期：2026/3/17

## 1. 调试结论先行：这次卡死/跑飞的罪魁祸首

这次问题不是单点故障，而是“高半执行路径改造”过程中连续暴露出来的两级根因，二者都和“地址语义不一致”有关：

第一层罪魁祸首是**启动交付形态仍走 ELF (`-kernel kernel-rv`) 而不是 `.bin`**，导致我们把链接地址抬高后，启动入口与实际装载行为不一致。这个问题的直接后果是：OpenSBI 的 Next Address 语义与我们预期的“低物理装载 + 内核自建高半映射再跳转”模型发生冲突，内核要么起不来，要么落入混合地址路径。后续我们改成 `.bin` 后，日志恢复为可控状态，`Domain0 Next Address` 稳定在 `0x0000000080200000`，说明入口回到低地址物理可启动模型。

第二层、也是导致你看到 `rv-ktrap` 的直接罪魁祸首是**页表访问和页表遍历都仍带着“仅 4KiB 末级页表”假设**，而我们实际引入了根级 1GiB 大页叶子项（高半线性映射）。这里又拆成两个具体错误：

1) `PhysPageNum::get_pte_array/get_bytes_array` 直接把低物理地址当虚拟地址解引用，读到了未映射低地址。日志证据：
- `unsupported kernel trap: ... LoadPageFault ... stval=0x80000008 sepc=0xffffffc080292800`
- 其中 `sepc=...292800` 落在 `translate_va` 附近，`stval=0x80000008` 明确是低地址访存。

2) 修完第一点后，walker 仍把根级叶子项当“下级页表指针”继续解引用，形成第二次异常。日志证据：
- `unsupported kernel trap: ... LoadFault ... stval=0xffffffc080000008 sepc=0xffffffc080292822`
- `stval` 已经是高半地址，说明“地址别名”修对了，但把 1GiB 叶子当页表页去读，导致访问了错误结构。

最后通过 leaf-aware walker（识别 L2/L1/L0 叶子）后，系统稳定进入用户态，最终日志出现：`=== All tests completed ===`，证明问题闭环。

## 2. 适配思路与总体架构

这次适配遵循“参考 rustoswhu，但不盲抄细节”的原则，核心目标是把 rcore-lab 的 RV64 路径推进到可维护的多架构平衡点：

1. 启动阶段：低物理可启动；内核执行路径可抬高。
2. 页表阶段：允许根级高半大页映射；用户页表可继承内核高半根项。
3. trap 阶段：去 trampoline 依赖，使用 `sscratch` 栈切换 + `kernelvec/uservec` 双入口。
4. 运行阶段：用户态/内核态在统一地址策略下工作，不再靠散落的 `cfg` 临时补丁救火。

这套思路背后的关键点是“把不变量固定下来”：

- 不变量 A：QEMU/OpenSBI 启动仍从低物理入口进（因此顶层交付使用 `.bin` 更稳）。
- 不变量 B：内核长期运行地址语义以高半为主，物理页访问统一走高半别名。
- 不变量 C：页表翻译逻辑必须承认 Sv39 大页叶子是合法终点，而不是默认一定下钻到 L0。

这样设计后，RV64 与 LA64 的差异会被收敛到“硬件能力不同”的位置：

- LA64 通过 DMW 获取物理内存可达性。
- RV64 通过高半线性映射和页表叶子语义获取同等效果。

也就是说，两边都实现了“物理页可通过统一抽象访问”，只是实现机制不同。这个思路正是多架构维护真正需要的抽象边界。

## 3. 这次具体改动说明

### 3.1 启动链路：从 ELF 交付改为 BIN 交付

改动点：

- 顶层 `Makefile` 的 `rv/debug` 目标新增复制 `os.bin -> kernel-rv.bin`。
- 顶层 `run.sh` 的 QEMU 启动从 `-kernel kernel-rv` 改为 `-kernel kernel-rv.bin`。
- `os/Makefile` 的 `rv` 目标显式依赖 `$(KERNEL_RV_BIN)`。

意义：

- 对齐 rustoswhu 的“低物理装载 + 内核自管虚拟地址”启动模型。
- 避免高链接地址直接暴露给 OpenSBI/QEMU ELF 装载逻辑而引发不确定行为。

从日志看，改完后 `Domain0 Next Address` 固定为 `0x80200000`，说明入口回到预期模型。

### 3.2 物理页访问语义统一：全部走高半别名

改动点（`arch/src/riscv64/mm/address.rs`）：

- `PhysAddr::get_ref/get_mut` 改为 `(pa | VIRT_ADDR_START)` 解引用。
- `PhysPageNum::get_pte_array/get_bytes_array` 同样使用高半别名地址。
- `From<usize> for PhysAddr` 增加掩码处理，避免高位污染。

意义：

- 把“物理页如何被内核访问”统一成一个规则，而不是不同函数各自猜测当前地址语义。
- 这是高半执行路径稳定运行的先决条件。

### 3.3 页表遍历器重构：支持根级叶子/大页

改动点（`arch/src/riscv64/mm/page_table.rs`）：

- 新增 `find_leaf_pte`，遍历时遇到有效叶子即返回，不再强制走到 L0。
- `translate` 改为复用 leaf-aware 逻辑。
- `translate_va` 按层级计算偏移：
  - L2 叶子（根级）按 1GiB 偏移；
  - L1 叶子按 2MiB 偏移；
  - L0 叶子按 4KiB 偏移。

意义：

- 修复“把根级大页叶子当下级页表”这一直接崩溃点。
- 让 boot 阶段高半根项、运行阶段翻译行为、用户态地址翻译逻辑三者一致。

### 3.4 用户页表继承高半根项（已有改动的连贯性）

`PageTable::new()` 中仍保留了“克隆内核高半 root mapping（`0x100..0x1ff`）”策略。这个策略配合上面的 leaf-aware 翻译后，终于形成闭环：

- 克隆出来的不只是“能看见”，而是“能被正确解释”。

## 4. 为什么之前会出现“重复初始化日志”

你最早看到的是重复 `.text/.rodata/.data/.bss` 映射日志，这个现象本质是“系统早期进入异常后又回到近似初始化路径”，属于典型的地址语义错配连锁反应：

1. 内核刚建完映射开始驱动初始化。
2. 页表翻译在某次访存上踩到错误路径（低地址或错误叶子解释）。
3. trap 进入后无法稳定收敛到正常调度流，造成重复进入近似早期路径的观感。

修复后同样位置不再触发异常，日志自然推进到文件系统、网络、用户测试与收尾阶段。

## 5. 这次适配里“简化实现”和“困难点”

### 5.1 简化实现（刻意保守）

1. 启动链路先收敛到 `.bin`，不继续在 ELF 启动语义上做兼容分叉。
2. 先保证 Sv39 大页翻译正确，再谈进一步抽象（例如统一多架构 page walker）。
3. 先把“高半访问规则”做成硬规则，避免出现“这里要 strip、那里要 OR”的散乱风格。

这些简化看似保守，但它们减少了调试维度，对多架构长期维护反而是加分。

### 5.2 花时间最多的困难点

困难点并不在“改代码量”，而在“错误模型识别”：

- 第一次异常（`stval=0x80000008`）说明是低地址访问，但并不直接告诉你是哪个 helper 破坏了语义。
- 修完后第二次异常（`stval=0xffffffc080000008`）又变成高地址，容易误判为新 bug；实际上它是旧假设（只认 L0 页表）被高半大页映射放大后的第二层问题。

这类“连环根因”如果不按证据链逐层拆，很容易陷入反复打补丁。

## 6. 验证结果与稳定性判断

本轮统一验证命令：

- `LOG=INFO timeout 220 bash run.sh`

关键观察点：

1. OpenSBI 入口稳定：`Domain0 Next Address : 0x0000000080200000`
2. 不再出现 `rv-ktrap` 的 LoadPageFault/LoadFault。
3. 用户态测试长时间推进，包含 static/dynamic 混合测试路径。
4. 最终出现 `=== All tests completed ===` 并正常退出 QEMU。

这说明本轮改动已经把“早期跑飞”从结构性问题降到了可控状态，且不只是能开机，而是能完成完整测试批次。

## 7. 对后续重构的建议

1. 把“高半别名访问规则”进一步上提到 arch 抽象层，避免未来新增 helper 时回归。
2. 将 leaf-aware 页表遍历逻辑作为跨架构可复用模式，LA64 侧也可按硬件特性对齐语义边界。
3. 对 `clone_kernel_root_mappings` 的就绪时机做更显式约束，减少早期警告日志的噪音。
4. 对 `run.sh/Makefile` 的 RV 启动路径补一段注释，明确为什么必须走 `.bin`（防止后续误改回 ELF）。

总体上，这次改动的价值不只是“修了一个异常”，而是把 RV 高半执行路径、页表翻译语义、启动交付形态三件事拉到了同一套架构约束里。只要保持这套约束，后续继续推进多架构抽象（包括你关心的 `ArchInterface` 边界收敛）会明显顺畅。
