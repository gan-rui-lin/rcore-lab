# glibc 完整调试手册（rCore-lab）

本文档用于在 `rcore-lab` 中稳定复现、定位、修复 glibc 相关问题，重点覆盖：

- 如何正确跑 glibc 单测
- 如何用 `LOG=INFO / LOG=SYSCALL` 快速定位 syscall 层问题
- 如何识别“文件存在但 exec 返回 ENOENT”这类典型误判
- 常见坑位与对应修复方式

---

## 1. 调试前提与原则

1. `LOG`、`SINGLE_TEST`、`TRACE_PID`、`TRACE_NAME` 都是**编译期注入**（`option_env!`），不是纯运行期开关。
2. 因为是编译期注入，改这些变量后必须重新触发构建（`run.sh` 默认会触发）。
3. 单测优先从 `SINGLE_TEST` 入手，先缩小问题面再扩大到全量套件。

相关代码位置：

- `user/src/bin/initcode.rs`：`SINGLE_TEST` 分流与 suite 执行入口
- `os/src/logging.rs`：`LOG` 到日志级别映射
- `run.sh`：构建和 QEMU 启动入口

---

## 2. 标准调试命令

### 2.1 跑 glibc 单个 suite

```bash
SINGLE_TEST=glibc-lua LOG=INFO bash run.sh -f sdcard-rv.img -t all > glibc_lua_info.log 2>&1
```

```bash
SINGLE_TEST=glibc-libctest LOG=INFO bash run.sh -f sdcard-rv.img -t all > glibc_libctest_info.log 2>&1
```

### 2.2 打开 syscall 级追踪

```bash
SINGLE_TEST=glibc-lua LOG=SYSCALL bash run.sh -f sdcard-rv.img -t all > glibc_lua_syscall.log 2>&1
```

### 2.3 控制变量跑法（推荐）

```bash
env -u TRACE_PID -u TRACE_NAME -u RUN_EMBEDDED_PTHREAD SINGLE_TEST=glibc-lua LOG=INFO \
  bash run.sh -f sdcard-rv.img -t all > glibc_lua_info.log 2>&1
```

作用：避免历史环境变量污染调试结果。

## 3. 日志快查模板

### 3.1 判断测试是否真的开始

```bash
rg -a -n "Running /glibc/|OS COMP TEST GROUP START|testcase .* success|FAIL|completed \(status=" <log>
```

### 3.2 快速抓 syscall 失败码

```bash
rg -a -n "num=.* ret=-" <log>
```

常见返回码：

- `-2`：`ENOENT`（路径/解释器缺失最常见）
- `-10`：`EAGAIN`（如 `wait4` 轮询时常见，通常非致命）
- `-22`：`EINVAL`（参数或 flags 组合不被支持）

### 3.3 针对 `.so` 与解释器问题

```bash
rg -a -n "openat-so|PT_INTERP|interp|ld-linux|\.so|execve.*ret=-2|not found" <log>
```

## 4. 典型问题与定位方法

## 4.1 `./test.sh: not found`，但文件明明存在

现象：

- shell 打印 `./test.sh: not found`
- `execve("./test.sh", ...) -> -2`
- 镜像内确实存在 `test.sh`

根因：

- `test.sh` 是脚本，真正失败点常是 shebang 解释器不存在，而不是脚本文件本体不存在。
- 例如 shebang 为 `#!/bin/busybox sh`，但 `/bin/busybox` 未建立链接。

修复：

- 在 `activate_runtime_profile()` 内补 `/bin/busybox -> <root>/busybox` 硬链接。

---

## 4.2 `clock_gettime` 在 glibc 下频繁 `-22`

现象：

- `num=113(clock_gettime) ... ret=-22`

根因：

- 内核仅支持少数 `clock_id`（如 `0/1`），glibc 实际会探测更多 `clock_id`（如 `5` 等）。

修复策略：

- 扩展常见 `clock_id` 支持集合，并统一映射到当前时间源。

---

## 4.3 `fstatat` 在 glibc 下频繁 `-22`

现象：

- `num=79(fstatat) ... flags=0x1000 ... ret=-22`

根因：

- glibc 常使用 `AT_EMPTY_PATH (0x1000)`；若内核不支持，会返回 `EINVAL`。

修复策略：

1. 支持 `AT_EMPTY_PATH` 语义（空路径 + `dirfd` 场景）
2. 做 flags 合法性校验，拒绝未知位
3. 复用 `stat_from_fd/stat_from_path` 保持行为一致

---

## 4.4 ext4 mount 失败 `rc = 95`

现象：

- 启动后很早 panic，日志出现 `ext4_mount: rc = 95`

常见原因：

- 镜像被宿主机 loop 挂载占用或处于异常状态（尤其是替换镜像文件后旧挂载残留）。

排查：

```bash
mount | rg "sdcard-rv.img|/mnt/sdcard"
```

建议：

- 调试前确认镜像未被宿主机挂载占用，必要时先卸载再启动 QEMU。

## 5. 本轮 glibc 调试已落地修复

1. `user/src/bin/initcode.rs`

3. `os/src/syscall/process.rs`
   - `sys_clock_gettime()` 扩展常见 glibc `clock_id` 支持

## 6. 推荐调试流程（可直接照抄）

1. 先单测一个 suite（例如 `glibc-lua`）：
```bash
SINGLE_TEST=glibc-lua LOG=INFO bash run.sh -f sdcard-rv.img -t all > glibc_lua_info.log 2>&1
```

2. 看是否真的开始执行 testcase：
```bash
rg -a -n "OS COMP TEST GROUP START|testcase .* success|FAIL|completed \(status=" glibc_lua_info.log
```

3. 若出现 not found / fail，再看 syscall ret：
```bash
rg -a -n "num=.* ret=-" glibc_lua_info.log
```

4. 仅在必要时切换到 `LOG=SYSCALL`，避免日志过大。

5. 修复后重复同一单测，确认关键错误码归零，再扩大范围到 `glibc-libctest` 或全套。

---

## 7. 验收标准（glibc 方向）

最小验收：

- 指定 glibc suite 能完整跑完（有 `OS COMP TEST GROUP END ...` + `status=0x0`）
- 不再出现由解释器缺失导致的 `execve ... ret=-2`
- `clock_gettime ... ret=-22` 归零或显著下降
- `fstatat ... ret=-22`（特别是 `flags=0x1000`）归零

---

## 8. 附：常用 grep 片段

```bash
# 看所有失败用例
rg -a -n "FAIL|fail|failed|not found|Segmentation|panic|ret=-" <log>

# 看动态加载相关
rg -a -n "openat-so|PT_INTERP|interp|ld-linux|\\.so|dlopen|dlsym" <log>

# 看某个 syscall
rg -a -n "num=79\\(fstatat\\)|num=113\\(clock_gettime\\)|num=221\\(execve\\)" <log>
```

## 9. 备注

本手册聚焦“glibc 在当前内核实现下的可执行调试路径”，目标是快速定位兼容性缺口，而不是一次性补齐所有 Linux 语义。建议每次改动都保持“单测可复现、日志可回归、错误码可量化”。
